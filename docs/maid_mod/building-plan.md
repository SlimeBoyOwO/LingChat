# 建筑：女仆发起，导演出蓝图，模组施工

状态：一期（插件与导演 Agent 的桥接）已实现，待真机。宿主只提供通用的导演任务循环，
建筑提示词与提交工具定义都在插件；蓝图内部格式、导演生成工具与模组施工器留到后续期，
本文先把需求、边界与已经定下来的接口写清楚。

二期先行（2026-11-21）：为了先验证「模组能不能不经过 LLM 自己按图施工」，模组加了通用
施工帧 `maid_build`，插件加了 `maid_build_house`，蓝图暂时写死成一座 11×11 的中型木屋。
这条链与导演任务并存，导演产出的蓝图以后接同一条施工帧；细节见下文「先行实现」。

## 需求

玩家对女仆说「给我盖一座小屋」这类话时：

1. 女仆调用一个规划工具，参数是建筑描述与规模；工具立刻返回，不占住她这一轮对话。
2. 宿主把任务交给一个单独运行的导演 Agent。导演拿现场地形、她的背包与最近对话，
   在自己的工具循环里生成一份建筑蓝图。
3. 蓝图不交给女仆。生成完成后宿主通知插件，插件按任务 id 取走蓝图；转给 MC 模组
   在后续期，模组之后操作女仆一块块施工。
4. 生成期间女仆照常聊天。完成后她只拿到一句短摘要，知道「要建的是什么、大概多大」，
   不需要背下整份蓝图。
5. 玩家中途问「建得怎么样了」，女仆能查当前任务是生成中、已完成还是失败。

## 已经定下来的取舍

## 角色分工

```
女仆 LLM
  └─ maid_plan_building（插件工具）
       └─ 宿主 director_task_start（插件 host API，通用任务循环）
            └─ 导演后台任务（god_agent/task）
                 ├─ 任务说明与提交工具 schema：插件给
                 ├─ 最近对话：宿主从 GameStatus 取
                 └─ 现场与锚点：插件从模组快照取
       └─ 完成信号 director_task
            └─ 插件取走蓝图，之后转给模组（本期不做转发）
```

女仆与导演是两个独立的 LLM 运行位。女仆的工具调用只负责投递任务；导演在后台跑工具
循环，不写台词表、不进主对话、不流式展示。

## 接口契约

### 插件工具

`maid_plan_building`

| 参数     | 类型    | 说明                                                   |
| -------- | ------- | ------------------------------------------------------ |
| `prompt` | string  | 想要什么样的建筑，必填                                 |
| `scale`  | string  | `small` / `medium` / `large` / `custom`，默认 `medium` |
| `width`  | integer | 可选，宽（x 轴）                                       |
| `height` | integer | 可选，高（y 轴）                                       |
| `depth`  | integer | 可选，深（z 轴）                                       |

`custom` 必须给齐三边。其余等级不给尺寸时按该等级的边长上限；给了但不能超过上限。
本期尺寸上限：

| 等级   | 最大边长（方块） |
| ------ | ---------------- |
| small  | 9                |
| medium | 17               |
| large  | 33               |
| custom | 33               |

单张蓝图的方块数目标上限约 4000。本期蓝图格式未定，无法按块数校验；第二期选定格式
后把它落成硬限制，避免一次生成与施工都过重。

工具成功只表示任务已受理，不返回蓝图。正在生成时再次调用会被拒绝。

`maid_building_status`

无参数。查当前插件最近一次建筑任务：生成中 / 已完成 / 失败；完成时带导演给的短摘要。

### 宿主 host API

插件需在 manifest 顶层声明 `director_task = true`，未声明一律拒绝。

`director_task_start(kind, request)`

- `kind`：任务标签，只用于任务 id 与信号回传；本期插件传 `building`。
- `request`：通用任务请求，包含任务说明、用户消息与提交工具定义，结构见下。
- 返回 `{ok: true, task_id}` 或 `{ok: false, error}`。
- 立刻返回。已有任务在跑时拒绝，不排队。

`director_task_status(task_id=None)`

- 省略 `task_id` 时查当前插件最近一次任务。
- 返回 `{ok: true, task: {...}}` 或 `{ok: true, task: null}`。
- 任务快照字段：`taskId`、`kind`、`status`（`running` / `done` / `failed`）、
  `summary`、`error`、`hasResult`、`startedAt`、`finishedAt`。

`director_task_take(task_id=None)`

- 取走任务结果（蓝图），取走后 `hasResult` 变为 false。
- 返回 `{ok: true, taskId, kind, summary, result}`；任务未完成或没有结果时返回错误。

### 宿主信号

信号名 `director_task`，只派发给发起该任务的插件。

payload 顶层字段：

| 字段        | 说明                       |
| ----------- | -------------------------- |
| `taskId`    | 任务 id                    |
| `kind`      | `building`                 |
| `status`    | `done` / `failed`          |
| `summary`   | 导演给的短摘要，失败时为空 |
| `hasResult` | 是否有可取的蓝图           |
| `error`     | 失败原因                   |

插件在 handler 里按 `taskId` 调 `director_task_take`，再写旁白、请女仆开口；转给模组
在后续期。

### 请求结构

宿主只认通用信封，建筑语义都在插件里：

```json
{
  "system_prompt": "你是建筑导演，负责……",
  "prompt": "【建筑愿望】……【规模】……【现场】……",
  "include_recent": true,
  "submit": {
    "tool": "submit_building_blueprint",
    "description": "提交最终的建筑蓝图。",
    "parameters": {
      "type": "object",
      "properties": {
        "summary": { "type": "string" },
        "blueprint": { "type": "object" }
      },
      "required": ["summary", "blueprint"]
    },
    "result_field": "blueprint",
    "summary_field": "summary"
  }
}
```

插件负责：

- `system_prompt`：建筑导演的角色、规模限制、坐标约定与禁忌。
- `prompt`：建筑愿望、规模与现场（地形、背包、锚点）；最近对话由宿主追加。
- `submit`：提交工具的名字、描述、JSON Schema，以及结果与摘要从哪两个字段取。

宿主只校验文本字段非空且不超上限、提交工具定义是 object 且不超体积、`kind` 是短标签。
结果序列化后不超过 2MB；摘要不超过 240 字。

现场的字段（`dimension`、`anchor`、`terrain`、`inventory`）由插件组装后写进 `prompt`，
宿主不解释。锚点坐标取发起那一刻的她；蓝图里的相对坐标以锚点为原点，y 向上，这条约定
写在插件的任务说明里。

### 导演任务的生命周期

- 单任务：同一时间只跑一个建筑任务；完成后结果留在槽位里等插件取走，下个任务顶掉它。
- 仅内存：重启即失；任务结束时若发现存档换了，按失败收尾，不把旧存档的蓝图当新存档的。
- 超时：300 秒；超过即失败并通知。
- 工具轮次：最多 6 轮。
- 失败：LLM 报错、超时、没有调用提交工具，都只通知失败，不自动重试。
- 取消：本期不做。

## 先行实现：写死木屋（测试施工链路）

目的不是把蓝图功能做掉，而是先用一份固定图纸验证第三期的施工器是否够用：玩家说
「帮我造个小房子」时，女仆调用 `maid_build_house`，插件把图纸发给模组，之后放方块、
走路、缺料判定全在模组里按 tick 推进，**不再逐块经过 LLM**。只有缺材料、走不到、
被别的事打断和盖完这几种情况才通过事件旁白请她开口。

### 流程

```
女仆 LLM
  └─ maid_build_house（插件工具，无参数）
       ├─ 问一次 maid_state：当前位置与朝向（施工锚点锁定在这一刻）
       ├─ 生成 11×11 中型木屋图纸（插件内固定，按她的朝向旋转）
       └─ 发 maid_build 给模组，立刻返回
            └─ MaidBuildController（模组，每 tick 推进）
                 ├─ 先低层后高层，够得着就放
                 ├─ 生存模式从她背包扣方块；主人创造模式不扣
                 ├─ 缺料记短路，继续放别的
                 └─ 收尾推 maid_build_done 事件
                      └─ 插件写旁白并请她开口（紧急事件）
```

### 图纸与锚点

- 图纸是一组相对锚点的格子：`{"x","y","z","block","facing"?}`，方块用注册表 id，
  目前只支持普通方块与门这类能由 `BlockItem` 放下的东西。
- 锚点由玩家准星决定：指着哪一格地面，图纸就以那一格为中心，它上面一格起算施工区。
  插件发 `anchor: {"looked": true}`，模组自己取主人准星射线；玩家不在同一维度、没指着
  方块时如实拒绝。图纸仍按她的 yaw 每 90 度旋转一次（决定门朝哪边），台阶这类有朝向的
  方块跟着转。
- 模组在锚点附近取地板所在的最高地面，把整张图纸抬到地面之上；地面高低差太大时
  会有格子悬空或放不下，按 `no_support` / `blocked` 如实记账。
- 准星指着上一座没盖完的工地（上一座格子范围外扩一格）时续建；指着别处则另起一座。

### 固定木屋

11×11，四层墙高。地基外圈石砖、屋里铺云杉木板；墙脚一层石砖，上面三层云杉木板，
四角与三面中柱是橡木原木，门框也是原木。正面中间一扇橡木门，其余四面开两格高的
玻璃窗（正面两对、背面两对、两侧各两对）。屋顶从墙顶外挑一格，再分六层向内收成
云杉台阶金字塔，顶脊压半砖；后墙偏东有一根穿过屋顶的石砖烟囱（里面不放火）。
门廊有两根原木柱撑住屋檐，柱间两段橡木栅栏、中间留一格宽的进出口，屋檐下挂两盏
灯笼；正面与背面各挂两支火把。整座约 763 格。

### 接着盖，不是另起一座

上一张图纸没盖完时，再调用一次 `maid_build_house` 会回到原来的工地，而不是按她此刻
的位置和朝向新建一座。做法有两层：

- 模组把图纸签名按四个旋转方向归一（坐标与方块朝向一起转），插件按她当前朝向重新
  生成的图纸也能认出是同一张；
- 签名命中后直接沿用上一轮算好的世界坐标，不再用新锚点和新格子，半成品不会和新朝向
  错位。她走远了也一样，模组会走回工地；只有工地所在的区块没加载、或超出她的活动
  范围时才拒绝，并说明原因。

只有上一座已经 `done` 时再调用才会新建；重新开始一局游戏后内存里的工地也会丢。

### 施工判据（借鉴 numen）

- 每格只有几种情形：已经对上、被别的东西占着、是液体、缺料、够得着就放、够不着。
- 一层一层来：只处理当前最低的未完成层；这一层连续几遍没有新进展，先把这层剩下的
  格子放一放、换下一层。门在施工期间一直留着，等别的格子都处理完再回门那一层装。
- 放一放的格子不急着判死：整张图纸都过完之后，把这些格子放回来补试一轮。别的方块
  放好之后，原来缺依托、被挡住、走不到的格子常常就能放了；补试过还是不行的才计入
  失败，然后收工。每一格只补试一次，不会在同一处反复打转。
- 支撑面还没出现的格子先跳过，不算失败；等下层放好，它下一遍自然会变成可放。
- 落脚点优先站到已经盖好的图纸格上，让建筑自己当脚手架；其次才是自然地面。
- 同一批候选按寻路步数挑最短的，而不是按直线距离；够得着按眼睛到方块外壳 4.5 格算。
- 同一层按由远及近的顺序放：先做离她远的那一头，边放边往自己这边退。反过来先放近的，
  会在身后留下一圈没放的格子，人退不出去，也没法从外侧绕。
- 自己正站在目标格里、周围又没有实地可站时（屋顶、墙头边上就是空的），先在与脚下同一层
  的邻格垫一块、站过去，再放这一格；邻格本来站得住就直接走。
- 目标明显在下面（差两格以上）时先跳下去：按跑跳规则找一个比她低、离目标不超过四格的
  实地落下去，落地之后按平地上的距离重新选站位。她自己的寻路不跳崖，站在屋顶上算不出
  墙根那几格的路。
- 每放一块之间有 4–7 tick 的随机间隔；下一格要转的角度越大，再多等最多 5 tick，
  不让她像 for 循环一样一块接一块。
- 放置要求她眼睛到落点之间没有方块挡着；同一块支撑方块从别的面绕进去也算被挡，
  隔着一堵墙或一根柱子把方块放到背面是不行的。支撑面仍优先用玩家指的那一面，但只
  接受看得见的；够得着却看不见时先换站位，换不到才退用别的可见面或者这一格记
  `no_sight`。
- 选落脚点先看「从那个站位能不能看见这一格」，看不见的候选直接跳过。墙背面的格子
  只剩外侧地面可选，她才会真的走出屋子去放，而不是在室内换着位置打转。
- 换站位有记忆：同一个格子试过的站位不再选；换到四次还放不上就停，这一轮先记着，
  等补试轮再试。
- 走路判死看她自己有没有真的位移，不看到落脚点的直线距离：绕路时离目标本来就是先
  变远的，按距离判会把正常绕路当成走不通。
- 到站要真的踩进选好的那一格，差一步不算：站位的视线校验是按那一格的眼睛算的，
  在两格外就开工作废了这次选择；她还没到之前，那个格子也不会被当普通方块放掉。
- 建筑期间免摔落伤害：从屋檐直接下到地面去做外墙、门廊这类活时不必先垫一路，跑跳的
  落深在这时放宽到十格，落点上方整根柱子验空才跳。
- 目标格被别的方块占着时先走过去把它挖掉，掉落按挖掘那一套进她背包（工具、耐久、
  背包差分都照挖方块处理），再放图纸这一块；挖不动的（受保护方块）才记 `blocked`。
- 目标格被自己站着就先挪到旁边的站位；被别的活物占着就先放一放，五秒后再试，不记
  失败。
- 原木、石英柱这类带朝向轴的方块放好后强制竖直，不按她点到的那一面横过来。
- 垫脚方块在她走路、垫下一块、原地起跳的途中都不拆，到站之后才收拾；垫脚位置要用
  两格高（脚加头），头顶被房顶卡住时先走到附近露天的地方，再沿外墙往上垫。
- 目标与她齐平或只高一格时也垫：屋顶那一步常常是「离屋顶还差一格」，先在她脚下这一层
  放一块、走上去，再从上面把屋顶放掉；垫完就能放的位置优先，方向不必朝向目标。
- 头顶两格被压住时先不垫：那种地方她跳不起来也迈不上去，换个站位或者先走到露天处；
  收尾原因里单独记一条「头顶太低」，不再当成走不过去。
- 落脚点搜索每 tick 有寻路额度（6 次）：屋里屋外不通时，逐个候选算路会把整个服务端拖住。
  额度用完就先歇，游标停在原处，下一 tick 接着扫，不按「这一遍没进展」记账。
- 从她当前站的位置算过、走不到的站位会记下来，她没挪窝、世界也没变之前不再重算；
  屋里看不见的屋顶高台就靠这一条被逐轮跳过，搜索才能走到外面的地面落脚点。
- 跑跳路线每 tick 只算一条，同一步没算通隔两秒再试，不反复重算整条路线。
- 施工期间按住她自己的随机游荡、捡东西与工作模式：跟随让路，捡物与溜达不启动，
  原来挂着的工作模式（农场、钓鱼……）先切成空闲，收工时换回去，免得她中途跑去干活。
- 走不过去的格子先试跑跳：缺口另一头有站得下、看得见这一格的位置时，跳过去放，不垫
  方块。跑跳的校验与上限见下文「跑跳（跨缺口）」。
- 缺料不硬等：这一格记 `short_of_material`，别的能放继续放；收尾时把每种方块还差
  几件交给插件，补料后再调一次 `maid_build_house`，已经盖好的格子会自动跳过。
- 收尾原因拆开：缺料、被占、液体、旁边没站位、走不过去、被活物占着、放失败。
- 主人是创造模式时不扣料，方便测试整条链。

### 代码结构

施工逻辑按职责分在六个文件里，都在 `action/construction/`：

- `MaidBuildController`：对外接口与会话生命周期。受理、恢复、取消、每 tick 推进、收尾事件、
  调试上报，以及 `Run`/`Cell` 两份运行时状态。
- `BuildRules`：纯规则，不碰世界。格子的五个状态（待做、搁置、补试中、完成、失败）、
  失败原因枚举、一层扫完后的去向，以及「这一格此刻是什么情况」的判定表。单测覆盖。
  去向是一串有序动作（`PassEnd` 持有动作列表），执行到收工为止。
- `BuildPlanner`：选格与落子。观察一格、查判定表、决定挖掉/走过去/放置，负责站位搜索、
  视线校验、原地能放的快路径，以及调试用的「下一块放哪」。
- `BuildMoves`：动作执行。走路、垫托底/顶块、原地起跳、跑跳各是一个动作对象，由
  `Run.move` 单一字段持有；同一时刻只允许一个动作在跑。垫脚方的拆放也在这里。
- `CellFlow`：一格的进度状态机，也是唯一能改 `Cell.state` 的地方。每次迁移先跑退出行为
  （放开为它占的落脚点、交出手上这一格），再跑进入行为（记账或补试重置）。调用方只上报
  结局：放好、这一遍先放着、搁到补试轮、收账；「换满站位后升级为搁置」「补试轮里升级为
  收账」这两条规则只有这一份。
- `BuildLayer`：一层走完后的去向执行。数一遍的进展与停滞，交给 `BuildRules` 决策，再按
  动作列表顺序执行；动作分发是穷尽 switch 表达式，新增动作必须在这里实现。

判定顺序固定为：已符合 → 液体 → 被占（能挖/不能挖）→ 缺料 → 被活物挡 → 自己占着 →
需要看距离和视线。以前这段是 `work()` 里一长串 if，同样的条件在「原地能放的先放」「到站
后试放」「调试预测」里各有一份；现在三处共用 `observe()` 和 `BuildRules.verdict()`。

### 垫脚与跑跳

主流建造工具都没有「高度不够时自动搭脚手架」；numen 的答案是低层先建、用建筑自己
当脚手架，够不着就如实报错。真正能补上屋顶的是移动层的宏动作。一格以内的落差由
「往旁边垫一格走上去」和「原地起跳把脚下补上」解决；跨过缺口则用跑跳：平地最远
四格，抬一格只剩三格，跳得过去就不必垫方块。

触发是兜底式的：某一格找不到能站过去的位置，而且它不在她脚下（垫不到更低处去）。
位置只在她脚下这一层、四面各一格的范围里挑，只往上下左右四个方向垫（斜着放会让她
从斜角起跳，被旁边的方块挡回原高度）。目标还高过脚下两层时是往上爬，每一步都必须比
现在更接近目标；目标与她齐平、或者只高一格时不看远近，改看「垫完站上去这一格放不放
得下」——屋顶那一步多半是这样，边上常常只有离开屋顶的那一侧还有空位，先垫上去再走
回来才是能走的路。顶块下面没有依托时，先垫托底那块，下一 tick 再放顶块并走上去。
走向垫脚块时要求她真的踩进那一格，差半格不算到站。同一格最多垫 6 次、一场施工最多
16 块；目标高过 12 格、水平超过 8 格就不垫。垫脚料从她背包里出（创造模式不扣），她离开之后逐块
拆掉还回背包，拆不下的掉在脚边。收工时她会先走到旁边的实地站好，再拆剩下的（包括刚才
踩着的那块），然后才推收尾事件；实在没地方去就等一会儿直接拆，让她落回地面。

原地垫柱单独一条：四面都垫不出去（贴着墙、被围住），或者目标就在正上方时，她原地
起跳，脚一离地就把方块补进原来站的那一格，落下来就升了一层。起跳要三格净空（脚、
头、跳起来的那一格），两格高的夹层里跳不起来，这时还是交给「先出屋」那条路。

### 平着搭路与依托

目标是齐平的、中间又走不过去时，往上垫解决不了问题：每垫一格就高一层，到头来还是
够不着也看不见。这时按玩家在起床战争里的铺法平着搭：朝目标差得多的那条轴挪一格，
前面本来就站得住就直接走过去，悬空就在脚下同一层铺一块再走过去，人始终走在同一个
高度。同一格最多铺 8 块，排在跑跳之后、垫脚之前，选站位与兜底两条分支都接上。

格子四周一个能贴的面都没有时不再干等：先看它正下方是不是草、雪、高草这类可替换的
方块——原版点下去会把这些方块本身换掉，落点对不上目标，于是永远「没有依托面」。
把那一块换成实心垫脚块，目标就有面可贴；每格只垫一次，收尾时随垫脚块一起拆掉。
还是放不下的（四面真悬空、又够不着）仍按原样跳过，等上下层的格子先就位。

垫脚块按「为谁搭的」记账：每块记着它服务的那一格，那一格还开着（待做、补试中）就不拆，
放好或收账之后才按远近清理。只按「离她近、她正在走」护着是不够的——她还没走到桥上的
那一格，桥就先被当成没人用的临时方块拆掉了，寻路随之失败。

寻路失败还有一条退路：选站位、跑跳、搭路、垫脚、出屋全都试过仍不行，而她脚下踩的是
自己垫的方块或桥时，跳回目标附近的地面，丢掉在高处试出来的那批站位，下一 tick 从地面
重新开始。她自己的寻路不跳崖，站在桥或柱子上时很多站位根本走不到，困在半空里反复算
没有意义。

### 施工期间不分心

施工一盖就是十几分钟，这段时间里不能让她再被自己的 AI 拽走。跟随行为的远距离传送由
长任务让路挡住；空闲日程里的「四处看看 + 随机走动」与「跑去捡地上的东西」在施工期间
不启动；她原来挂着的工作模式（农场、钓鱼、攻击……）会与她抢同一条寻路，施工开始时先
切成空闲，收工或被打断时再换回去，界面与存档里的模式跟着一起恢复。

寻路本身也要有预算：屋里屋外不通时，逐格逐候选地算一遍能把主线程拖住。落脚点搜索每
tick 只算固定的几次，算不完就留到下一 tick；从当前位置算过走不到的站位会记下来，她没
挪窝之前不再重算，搜索才能从屋里那些走不到的屋顶高台挪到外面的地面上。跑跳路线同理，
每 tick 只算一条。

### 调试寻路

`/tlml pathing show`（需要管理员，单人游戏要开作弊）盯住离执行者最近的那只女仆，
她施工时用原版粒子实时画出这一 tick 的判断：手上那一格（白框，走路时是目的地、放的时候
就是正在放的方块）、选定的落脚点（绿框）、真正在走的 A* 路径（glow 点串）、眼睛到目标格的
射线（淡青蓝，被挡时画到挡路的方块并标红）、选站位的搜索范围（蓝线框，先扫目标四周 4 格、
往下 6 往上 3，一处都站不上时扩到 6 格、往下 8 往上 5），以及这一 tick 试过的每个候选站位
——红走不到、橙看不见、黄够不着、灰试过、浅绿能走；下一块大概率要放的位置（含接下来要垫的
方块）用幽蓝火苗框标出，半秒左右重算一次。蓝框选的是落脚点而不是放方块的位置，所以框永远
以目标为中心，她自己站的那一格也直接算候选。手上的格子没做完之前施工程序不会换目标：
走到一半没走通、到站了却看不见，都是换站位重试同一格，试满四次才搁到补试轮。show 后面可以跟名字
只开其中几部分（path、stand、target、ray、search、probe、hop、place），不跟名字是
全部开 / 全部关；
hide 带名字只关那几部分。`/tlml pathing status` 打印阶段、目标（连方块名）、落脚点、寻路额度余量与
当前开着哪些部分；额度剩 0 就说明她卡在算路上。收工、换存档会自动停，重开游戏要重新 show。

### 跑跳（跨缺口）

跑跳只在找不到能走过去的落脚点之后才试，并且排在垫脚前面：一条三格宽的沟，跳过去
只要十几 tick，垫三块方块则要放、要走，收工时还要拆。规则沿用玩家那一套：平地最远
四格，往上抬一格只剩三格，往下最多落三格；只沿四个方向直线跳，不模拟斜跳、助跑与
惯性。她站在高处、目标却在下面（典型是屋顶上要去处理门廊或围墙）时，落深放宽到十格，
并且允许紧贴一格往外落——建筑期间摔落伤害已经免掉，直接从屋檐下去，不必先垫一路。

起飞前逐格校验：起跳格与落点格都要站得下（脚与头两格空、脚下有实地），中间飞行包络
里不能有实心方块，断口下面三格内不能是液体、岩浆、火、岩浆块、仙人掌、甜浆果、细雪
这类。落深超过三格时还要把落点上方的整根柱子验到起跳高度，不能从屋檐或楼板里穿下去。
深谷可以跳：弧线是按落点提前算好的，不会半路掉下去；近处有岩浆才改垫方块。
起跳列与落点列还要多让出头顶两到三层，弧线抬高时不会从方块里穿过去。地面连续时不走
这条路——走过去更省；深落除外，它就是用来从高处往下走的。

执行不走 `WALK_TARGET`：女仆的寻路与任务每 tick 都可能写速度，靠冲量很难稳。施工器
自己按弧线摆位置，途中关掉重力、清掉速度，走完一段再验下一段。一条路线最多 5 跳、
最多展开 24 个落脚点；失败或被打断时退回当前这一段的起跳点，不把人留在半空。落点
记进这一格的换站位记忆，下一轮换别的路线或者退回垫脚。

前提是车万女仆的导航能走上一格新放的方块：`maid_build_climb_test` 用一根 2×2、8 格
高的柱子专门验这一点，最上面两层只能先垫上去；盖完就是能走，卡住时收尾原因会是
「走不过去」。

垫脚的触发也要靠选站位的视线判定：高处那几格没有任何可达站位看得见时，才会回到
「垫一格」这条兜底；垫过一次之后如果还有什么站位「够得着」，必须先确认它看得见，
否则会把垫脚分支顶掉，表现就是垫一格就放弃。垫脚上限按升高次数算（一次升高要放
托底和顶块两块，按块算会少算一半）。垫出来的方块在她走上去之前不拆，到站之后才
收拾；每垫一格要留出脚和头两格净空，头顶被房顶卡住时先走到附近露天的位置，再沿
外墙往上垫。

### 模组接口

`maid_build`（插件 → 模组）：

```json
{
  "maid_id": "…",
  "name": "小木屋",
  "anchor": { "x": 100, "y": 64, "z": 200 },
  "cells": [
    { "x": -2, "y": 0, "z": -2, "block": "minecraft:oak_planks" },
    { "x": 0, "y": 1, "z": -2, "block": "minecraft:oak_door", "facing": "north" }
  ]
}
```

回执 `maid_build_result` 只说明受理没受理、多少格、是否扣料。施工结果走事件
`maid_build_done`：`status`（`done` / `partial` / `failed`）、`name`、`placed`、
`total`、`remaining`、`reason_code`、`reason`、`materials`（`{item, count}` 数组）。
插件把 `maid_build_done` 标记为紧急事件：缺料、够不着、被打断、盖完都会请她开口。
`maid_build_status` 是同步查询，返回当前或上一座房子的 `status`、`placed`、`total`；
女仆的 `maid_building_status` 先问它，没有施工任务再退回导演任务进度。

### 本期不做

- 不做玩家结构保护、不做自动取材、不做液体处理；这些在第三、四期统一按 numen 的
  问题划分补。
- 不做重启后的进度恢复；施工锚点、上一张图纸与「上一座没盖完」只记在模组内存里，
  游戏重启后就没了，再调用会按她当时的站位另起一座。同一局里再调一次会接着原工地。
- 不做多任务；同一时间只有一张图纸在施工，新指令会顶掉旧的并推一条 `cancelled`；
  只有签名相同的图纸算「接着盖」。

## 蓝图格式（待定）

本期只约定「插件在提交工具 schema 里声明结果字段，导演提交一份 object」，内部结构
不锁死。后续从成熟的开源方案里选，避免自造一套没人能复用的格式。选型时要满足：

- 能表达方块 id、方块状态、相对坐标与调色板；
- 体积可控，适合模型分步生成；
- 模组能直接按它施工，不需要再猜语义；
- 能与选定的成熟格式互相转换，方便玩家导入现成建筑。

在格式定下来之前，插件声明的提交工具只要求结果字段是 object；宿主按通用上限校验
2MB，并原样保存。导演循环仍会真实调用 LLM 与工具，只是蓝图内容暂不保证可用。

### 参考实现：numen

本地参考项目 Numen（见 [reference.md](reference.md) 与其中的 `.archify/`）已经把
「模型设计 → 世界落地」跑通，后续选型与施工器可以直接借用它的分层：

- **设计入口**：`numen.shape` 用 WorldEdit 语义（长方体、球、线、生成函数）产出 `Cells`；
  Litematica 投影把 `.litematic` 读成世界坐标的 `Cells`；模型也可以直接写 `{name, pos}`
  的格子，一次最多 16384 格。
- **落地入口**：所有设计都收口到 `numen.build.diff / place`，先报差异，没差异就不派活；
  任务由 `BuildCompanionTask` 按 `CONSENT → WALK → WORK` 推进。
- **施工顺序**：先低层后高层；层内按清障 → 骨架 → 贴附件；托着别人的方块先立起来。
  够得着先放，够不着就走到最低那层能放的站位，不搭脚手架。
- **一格的状态**：`REACH` / `FAR` / `UNHELD` / `OCCUPIED` / `LIQUID` / `SKIPPED` /
  `DONE`，由 `BuildTask` 每刻按她站的位置重判；没放好的按 `dig_first` /
  `short_of_material` / `out_of_reach` 分组交账。
- **边界**：生存模式不挖立着别的方块（只回 `dig_first`），不自动取材（只报缺多少），
  带方块实体的方块不动，液体格不碰。寻路可挖可垫，但绝不挖 `PlacedBlocks` 里已经
  放好的建筑。
- **大脑**：目标存在 `goal.json`，步骤由 ReAct、`todo` 清单与任务槽三级推进；任务槽
  一具身体同时只一件活，新活顶掉旧活并以 `stopped` 收尾。

这些结论不要求本期照搬，但第二期的蓝图格式与第三期的施工器应优先复用它们的问题
划分，避免自造一套与现场状态对不上的模型。

## 分期

1. **本期：桥接**。宿主通用导演任务循环、完成信号、插件侧的建筑任务定义与发起/查进度
   工具、完成/失败旁白。模组不动。
2. **蓝图格式与生成工具**。选定成熟格式，做分层/分块的提交工具与尺寸、体积校验，
   让导演能稳定产出可施工的蓝图。
3. **模组施工器**。模组接收蓝图，锁定锚点，按依赖顺序取材料、放置、清理与收尾；
   施工进度推事件。
4. **施工通知与异常**。缺料、被打断、目标被占、玩家改主意时的旁白与恢复策略。

## 开放问题

- **朝向**：现有 `maid_state` 只给位置，没有 yaw。锚点本期只能锁位置；蓝图朝向先由
  导演按地形关系自行决定，后续需要模组补一个朝向字段。
- **材料**：背包只作为上下文，不保证够用。可以借鉴 numen：施工器不自动取材，缺料时
  按格记成 `short_of_material` 并报数，由女仆或玩家补料后再接着做；具体是停工、跳过
  后补还是先提醒，留到第三期。
- **施工范围**：可以借鉴 numen：生存模式不挖立着别的方块，只回 `dig_first`，由独立的
  挖掘动作处理；是否保护玩家已有的结构，留到第三期。
- **蓝图体积与 token**：大建筑不能要求模型一次吐出全部方块，第二期要按层或按部件分步提交。
- **进度与中断**：施工进度、玩家走远、女仆被打断、换存档时的处理留到第三、四期。
- **多任务**：本期单任务；以后若允许多个插件同时规划，再把槽位改成按插件或按存档分槽。
