# LingChat × 车万女仆：桥接方案与分期计划

把《车万女仆》（Touhou Little Maid，下称 TLM）接进 LingChat：游戏里玩家说的话进对话，角色的回话变成游戏内女仆气泡，游戏世界的变化记进台词表，最后让角色能真的指挥女仆做事。

两侧各一半：

- **插件** `data/plugins/mc_maid_bridge/`：随仓库分发，负责自然语言与策略（措辞、阈值、攒几条开口）。
- **模组** `extension/maid_mod/`：NeoForge 1.21.1 侧，负责游戏语义（谁在挨打、地形是什么、床在哪、怎么让女仆动起来）。与插件一起入库，但保持独立的 Gradle 工程与发布节奏；改完要自己构建并把 jar 拷进整合包。

两侧用一条本机回环的 WebSocket 通信（默认 `ws://127.0.0.1:48920`，协议见 `extension/maid_mod/README.md`）。上游社区有一份同类桥接（N.E.K.O × TLM），协议形状参考它，但本项目的插件系统形态不同，不能照搬它的常驻循环框架。

流程图（静态 HTML + 内联 SVG，直接打开）：[mc-maid-bridge-flows.html](mc-maid-bridge-flows.html)，包含总览、说话闭环、感知与开口、物品与投喂、动作工具五张图。

## 一条铁律：分工与顺序

**周期采样与变化判定必须在模组侧，自然语言与阈值必须在插件侧。** 理由：LingChat 的插件脚本每次调用新建解释器、跑完即弃，既没有定时器也存不下跨调用状态（见 `docs/plugin-dev-guide.md` 的「沙箱与限制」），「每隔几秒看一眼」和「跟上一次比」只有常驻且有 tick 的模组做得到。反过来，中文措辞、情绪提示、攒几条开口这类会反复调的东西放插件，改它们不用重编 jar。

**改动顺序永远是 宿主 → 插件 → 模组**：

- `PluginManifest` 带 `deny_unknown_fields`，先在 manifest 写宿主还不认识的新键，插件会直接加载失败；
- 插件脚本顶部的 `from plugin_host import ...` 一旦有一个名字宿主没有，**整个插件的所有 handler 全部消失**（现象是桥接彻底不出声，而没有任何报错落到日志里）。

### 一期：说话闭环

- 模组把「被监控女仆的主人在游戏里说的话」推成 `chat_message` 帧。
- 插件转成 `send_user_message("…")` 送进对话：原样一句，宿主按玩家行补上 LingChat 的用户名（2026-10-17 起不再加 `［Minecraft］` 标记，见下文）。
- 角色的回复经 `ws_send {type:"send_chat"}` 回到游戏，变成女仆头顶气泡（或聊天栏）。
- 宿主为此补了 `ws_request`（发一帧并等它的响应帧），后续几期都靠它。

### 二期：节奏对齐

模型的回复是流式到达的，连着几句几乎同时生成完。若跟着「生成完」外发，游戏里会一次涌出好几条。

改成订阅宿主新增的 `line_shown` 信号（由**前端主窗口**发出，只有它知道哪一句真的上屏了），逐句同步；连上 MC 时自动打开主界面的自动模式，否则角色说完一句就停住等人点继续，游戏里看起来跟断线一样。

2026-10-17 又改了一处显示口径：气泡不再往上叠。每句都**替换**上一句留下的气泡，头顶只留两枚——台词一枚，这一句情绪的颜文字一枚（情绪取自 `line_shown` 里的 `emotion`，插件按映射给出候选、模组随机挑一条）。车万女仆的气泡集合按到期时刻做键、最多堆五枚，所以替换得先清空再重新加，两枚气泡的停留时长也要错开 10 tick，否则同一毫秒加进去会算出同一个键、后者顶掉前者。

### 三期：感知与游戏事件

模组每 5 秒采一次样（`PerceptionSampler`），自己记着上一帧，**只在变化显著时**推 `event` 帧；判定逻辑是不认识 Minecraft 的纯函数（`PerceptionDiff`），能脱开游戏单测。

| `event_type`                           | 触发                                                     |
| -------------------------------------- | -------------------------------------------------------- |
| `state_snapshot`                       | 首次连上，或换了监控的女仆（未初始化那一档）             |
| `dimension_change` / `biome_change`    | 换维度 / 换群系（群系有 30 秒冷静期，鞘翅赶路不刷屏）    |
| `time_phase_change` / `weather_change` | 昼夜翻转 / 天气变化（没有天空的维度不报这两样）          |
| `low_health`                           | 玩家或女仆血量跌破阈值（边沿触发，回到阈值 ×1.2 才复位） |
| `maid_hurt`                            | 女仆挨打（一小段连续挨打合成一条，带攻击者与伤害类型）   |

插件把每条事件翻成一句只陈述事实的中文旁白，经 `add_prompt_line("narrator", …)` 写进台词表；紧急事件（`maid_hurt` / `low_health`）当场调 `trigger_proactive("")` 请角色开口，其余攒够若干件（配置项，默认 3）且**这期间没人说话**才请一次。连着的几件事并进同一行（2026-10-17 起，见「事件合并」一节）。

「这期间没人说话」不靠插件存计数器：往前读回最近几行，只数连续的事件旁白、并按行内「；」分出的段数计件——玩家发言与角色的回话都会插进这个连续段把它打断，计数于是自动归零。连着的重复开口由生成锁与主动对话的单槽队列挡住。

#### 空提示语的开口（2026-10-15 改）

`trigger_proactive("")` 表示**只开一次口、不写任何提示行**：宿主直接接着上下文生成一轮。原先这里传的是「你刚留意到身边有些变化，主动跟玩家说一句话，别复述数字。」，被宿主包成 `{旁白: （系统提示：…）}` 写进台词表——等于替角色决定了该看什么、该不该开口，还容易把语气带成复述报告。要说的内容本来就以旁白形式在上下文里，不需要再交代一遍；确实需要额外交代（如截图转述）时才传提示语。

顺带修掉一个显示缺陷：主动对话这条路写提示行时 `display_name` 留空，记忆构建会兜底成「未知」并给这行加上「未知: 」前缀（`add_prompt_line` 那条路带展示名「旁白」/「系统」，按规则不加前缀）。现在统一成 `PromptRole::System.display_name()`。

#### 名字要认得出是玩家

模组给的名字都是裸的：`maid_hurt.attacker`、`state_snapshot.player_name`、`chat_message.sender`。原样写进旁白，模型只会看到一个陌生的用户名（「你被 NoiQing_Ling 打了」），于是当成第三个人。三条处理：

- **聊天发言者恒为玩家**：模组只在「说话的人正是这只女仆的主人」时才转发（uuid 对不上直接丢），所以一律写成「玩家（用户名）说：…」，不依赖配置。
- **快照里交代名字**：`state_snapshot` 本来就带 `player_name`，写进第一句旁白（「你正和玩家（NoiQing_Ling）在主世界的平原」），模型由此知道这个名字指谁——不配置也能用。
- **挨打的攻击者要认人**：`maid_hurt` 的 attacker 可能是玩家也可能是僵尸，插件无从判断，所以加了配置项 `player_name`（你在 MC 里的用户名，可留空）；撞上它就写成「被玩家打了」。

**排查提示**：`trigger_proactive` 的每一次结果（受理 / 合并 / 被总开关拒 / 系统正忙 / 最终没能投放 / LLM 未配置）都会往宿主日志写一行，带插件 id 与提示语开头（空提示语显示为「（不带提示语）」）。看不到这条日志就说明插件根本没走到请求开口那一步（例如模组没推事件）。宿主日志在 `data/log/app/*.log`。

动作收尾（`action_done`）这类事件常常正好落在**自己这一轮生成的尾巴上**——工具刚受理就返回了，正文还在收尾，旁白此刻才到。所以宿主的投放不丢：请求先排进单槽队列，等这一轮台词播完、前端回到输入态再投放（20 秒冷却，队列 2 分钟过期），不会在生成中途插一轮。这也是「明明躺下了她却还说没找到床」的解药——那一轮里她本来就不知道结果（消息列表是本轮开头建好的），只能靠这次补上的开口交代。

## 四期：动作执行 MVP

### 目标

让 LLM 真的能指挥游戏里的女仆：走到玩家身边、走到最近的床边、坐下、站起、躺到床上、看向玩家。这一期的验收重点是「Tool RAG 召唤」与「工具意向能否变成真实动作」。

### 开工前先补的宿主缺陷（已补）

插件 manifest 里声明的 `[[tools]]` 原本**注册进 `ToolRegistry` 后永远不会下发给 LLM**：`ling-chat-plugins/src/manager.rs` 的 `register_tools` 只做了 `registry.register` 与 `add_available_tools`（后者按自身注释「仅用于展示，运行时不被读取、也不参与权限计算」）。而权限矩阵里，主聊天（`UserChat` → `scene_admin`，`all_tools=true`）取的就是 **default 角色组的 `tools` 集合**，插件工具从没进过那个集合——既不下发，**也进不了 Tool RAG 的候选池**（检索候选集就是权限集）。

补法：注册成功后授权、注销时收回（`set_tool_allowed_for_default_group`），收回时**不新建** default 角色组——那个入口会顺手造一个 `enabled = true` 的空组，而空工具集在 `all_tools` 场景下等于放行全部工具。配了两条回归测试。

**已知边界**：授权只落在 default 角色组，所以主动对话与剧本（走 `scene_normal`，工具集是内置工具的固定快照）**拿不到插件工具**——角色只在「玩家跟她说话」那一轮能动身体。这一期接受这个边界（也更安全）。

### 已定的取舍

- **移动目标只用语义**：`player`（玩家）或 `bed`（最近的床）。LLM 手上没有任何坐标（三期感知只推地形与血量），给坐标参数等于请它编数字。
- **移动类动作到位后立刻让角色开口**：模组推完成事件，插件记成旁白并复用三期的 `trigger_proactive`。
- **「躺下」用 TLM 原生睡床**：TLM 没有躺姿 API，只有 `startSleeping(BlockPos)`（女仆自己覆写过：回满血 + 涨好感）。够近直接躺，远就先走过去再躺。
- 同一时刻**只允许一个动作**在跑，新动作顶掉旧的；不做队列，不做上游那套「受理≠完成」三段式。

### 模组侧：帧与控制回路

```json
上行 {"type":"maid_action","data":{"maid_id":"...","action":"go_to|sit|stand|lie_down|look_at","target":"player|bed"}}
下行 {"type":"maid_action_result","data":{"accepted":true,"async":true,"action":"go_to","target":"player",
      "replaced_action":"","stood_up":false,"reason_code":"","reason":""}}
事件 {"type":"event","data":{"event_type":"action_done","action":"go_to","target":"player","status":"done|failed|cancelled",
      "reason_code":"","reason":"","elapsed_ticks":87,"distance":1.8}}
```

- `action` / `target` 全部白名单校验，**接口层面没有任何接受坐标的入口**（端口无鉴权，任何本地进程都能连：最坏也只能让女仆走两步、坐一下，不能执行指令）。
- `accepted=false` 表示「受理时就能判定失败」（附近没床、玩家不在同一维度、目标超出居家活动范围、女仆在睡觉/被骑乘/被拴），插件一次往返就知道结果，不留悬案。
- `async=true` 表示结果稍后由 `action_done` 给出（只有 `go_to` 与 `lie_down` 有完成事件）；三种结局（成功/失败/被顶掉）都推事件，否则插件会永远等一个不来的旁白。
- 计时用**内部 tick 自增**而非墙钟：单人游戏按 Esc 暂停时 `ServerTickEvent.Post` 不触发，天然做到「暂停不算超时」。

**位移不直接调 `getNavigation().moveTo()`，而是每 tick 往 brain 写 `WALK_TARGET` 记忆**，由原版 `MoveToTargetSink` 自己驱动导航（TLM 的 `MaidBedTask` / `MaidFollowOwnerTask` 也都是这么干的）：

- 女仆的 brain 里就有这个 sink（`MaidBrain:98`，优先级 2）；
- 反向做法是自杀：清 `WALK_TARGET` 会让 sink 的 `stop()` 立刻 `navigation.stop()` 把路掐掉；受理时只需 `eraseMemory(PATH)` 一次；
- 我们在 `ServerTickEvent.Post` 写（实体 tick 之后），是每 tick 的最后一次写；
- 附带好处：`MaidBedTask` 要求 `WALK_TARGET = VALUE_ABSENT`，所以动作期间 TLM 自己的找床与随机走动会自动让路。

**三条会「让她一动不动」的硬约束，必须如实失败而不是空等**：

- `MaidAwaitTask` 每 tick 会把落在禁足半径之外的 `WALK_TARGET` 直接 erase——居家模式下目标超范围就永远走不到，所以受理时预检直接失败。
- `MaidClearSleepTask` 每 tick：睡着但当前活动不是 `Activity.REST` 就叫她起床。活动由女仆的日程决定，**所以白天让她躺床会被她自己叫醒**，日程设成「全天工作」时更是永远睡不着。用几 tick 的确认窗口区分「真睡着」与「起身了」，起身就如实报 `not_sleep_time`；不强制切 `Activity.REST`（会和日程回切每 tick 拉锯，还会覆盖玩家自己设的日程）。
- 玩家开着女仆 GUI、或跟随模式下主人离得远时，TLM 自己的逻辑会抢走目标——归到超时/不可达，如实上报。

### 插件侧：五个工具（`maid_look_at` 2026-10-17 移除，见上表）

`manifest.toml` 里声明五个 `[[tools]]`，当时**都指向 `hooks.py`**（一个脚本可挂多个入口，不新开文件；2026-10-16 起改指 `tools.py`，见「代码分层整理」）：

| 工具名             | 用途                                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| `maid_go_to`       | 让女仆走到玩家身边或最近的床边                                                                                                      |
| `maid_sit_down`    | 让女仆坐下                                                                                                                          |
| `maid_stand_up`    | 让女仆站起来                                                                                                                        |
| `maid_lie_down`    | 让女仆走到床上躺下睡觉（她按自己的日程睡，不在睡觉时段会自己起来）                                                                  |
| ~~`maid_look_at`~~ | 2026-10-17 移除：她每说一句话，模组自己转头看主人（打架、干活、睡觉时除外）。当工具用会变成「说一句→调一次→再说一句」，纯粹浪费轮次 |

「看向玩家」改成**模组侧自动行为**挂在 `send_chat` 上：每冒出一句气泡就转一次头，不占动作槽（那会顶掉正在走路的动作）、不推任何帧、不给模型回执。协议里的 `look_at` 动作保留只为兼容。

`hooks.py` 加一个 `run(ctx)`（工具入口，与信号入口共用同一脚本），按 `ctx["tool_name"]` 分派（现已在 `tools.py`，分派从 if 链改成 `TOOLS` 表）：

- 未连上游戏 / 没绑定女仆 → 如实返回 `{"ok": false, "error": …}`，绝不假装已经执行；
- 经 `ws_request` 发动作帧（超时要明显小于工具自身超时）；
- 受理且即时完成 → 给一句事实（「已坐下」）；受理但要走过去 → 明确说还没到（「她正在走过去，还没到玩家身边」），免得模型以为已经到位；被拒 → 原样转达模组给的中文原因；
- `_handle_frame` 里加 `action_done` 的中文格式化。**它当场请角色开口**（不是攒够了才开口）：动作收尾正是玩家在等的那件事，攒着说就失去了「到位就说一句」的意义。`done` / `failed` / `cancelled` 三种结局都要能成话，被顶掉也要说，否则角色会一直以为还在做。

工具描述的第一句会进 `tool_search` 的清单（菜单只显示名字与首句用途），所以首句必须一句话说清这是什么能力——这也是 RAG 检索语料的一部分（语料是工具描述本身，用本地的中文嵌入模型算相似度；2026-10-17 起不再把英文工具名拼进语料，实测拼进去反而让中文短句的分数整体下移）。另外执行器只校验 JSON Schema 的一个子集，**不认 `enum`**，所以 `target` 的合法性要插件与模组两头各自兜底。

### 不做

- 不做跟随、工作模式切换、装备、挖矿、玩家受伤/成就等其余上游工具。
- 不做坐标参数，不做多动作队列与仲裁。
- 不新增宿主能力（不需要插件定时器与跨调用状态）。
- 不补工具级的 UI 开关（设置页只有组级开关，要收回插件工具就禁用插件）。

1. 宿主：`cargo check --workspace`、`cargo test --workspace`（含授权与收回的回归测试）。
2. 模组：`cd extension/maid_mod && ./gradlew build --offline`（46 个 JUnit 用例，其中 28 个是这一期新加的：参数白名单与归一、有无完成事件、最近床挑选与等距稳定、状态机的到位阈值两侧 / 超时 / 卡在床边 / 走不到早于超时 / 两阶段躺下 / 被自己叫起来 / 看向玩家收尾 / 「她不见了」最优先 / 只 tick 十次不超时）。
3. 插件：`py_compile` + 离线桩冒烟（临时目录、桩掉 `plugin_host`）：五个工具各自发出的帧与超时、中文结果、未连接 / 没绑定女仆时如实报错、被拒时原样转达、`action_done` 写成旁白并当场请求开口、未知工具名不炸。

## 五期：身边环境感知

三期让女仆知道世界的**全局**状态（维度、群系、天气、昼夜、血量、挨打），四期让她能**动**，
但她对**身边**一无所知：脚下踩着哪、正面对着什么、周围有没有生物、主人离她多远、看不看得见主人。
这一期补上这一层。

曾经想过「从她视角截一张图给视觉模型」。核过之后的结论是**不做**：模组是纯服务端的，服务端
没有画面，要出图要么另起客户端渲染（离屏帧缓冲 + 把相机搬到实体身上），要么在服务端软件
渲染（逐像素光线投射）——两条都比「结构化文字」贵一个量级。图留给将来「非图不可」的场景。

2026-10-17 补记：这一段的**理由仍然成立，结论下的范围太宽**。「模组没有画面」只说明不能从游戏
里出图，不等于拿不到画面——玩家的屏幕就在那里，LingChat 本来就有窗口截图能力（见文末「玩家
屏幕」一节，已落地）。当时引的研究依据也是读反的，见那一节的更正表。

### 借鉴

| 来源                             | 借了什么                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| 车万女仆自身的 AI（1.5.2+）      | **两段式注入**：最小集合自动进上下文、体积大的让模型调工具取（`query_game_context`）   |
| Voyager（NVIDIA 2023）           | 纯文本观察的字段表（附近方块与实体、血量、时间、位置），证明不给图也能感知世界         |
| CraftAgent                       | `LineOfSightData [items, entities, blocks]`：注视射线 + 看得见的方块/实体              |
| LLaMA-Rider（NAACL Findings 24） | 把**视野内**的东西连同数量编码成自然语言句子当观察——按需查询输出的就是这个             |
| DEPS（ICLR 2024）的 describer    | 视觉必须先压成文字再进推理                                                             |
| ROCKET-1/2（CVPR 2025）          | 别把原始帧当上下文，抽对象级信息                                                       |
| LMA（女仆附属模组）              | 被动感知走**边沿信号**（下雪/放晴/变暗），不推数值                                     |
| VistaWise（EMNLP 2025）          | 视觉信息应经轻量提取（token −30.7%）；Optimus-3 亦记「通用 VLM 在 MC 里 grounding 差」 |

### 分工照旧

**判据、档位、冷静期在 Java（模组），中文措辞与「紧不紧急」在 Python（插件）。**
两段式落地成两条路：

1. **她自发注意到**（模组每 5 秒采一次，只在变化时推 `event` 帧）→ 插件写旁白 → 攒够几条开口；
   （**身边那一层已经不这么走了**，见「身边感知的改法修订」：那里改成玩家开口时携带一次，
   只剩 `threat_near` 还当场开口。）
2. **按需「看一眼」**（玩家问「你周围有什么」时模型调 `maid_look_around`）→ 模组现取一份快照
   → 插件翻成几句事实当工具结果回给模型。

### 主动注意到的六类

| `event_type`              | 触发                                             | 为什么不会刷屏                                                      |
| ------------------------- | ------------------------------------------------ | ------------------------------------------------------------------- |
| `player_proximity_change` | 与主人的远近跨档                                 | 双阈值回滞（往近处果断、往回退多走两格）+ 5 秒冷却                  |
| `player_sight_change`     | 主人进出视线                                     | 要连续两次采样一致才认；他去了别的世界时不说这条（由 `gone` 交代）  |
| `threat_near`             | 附近从无到有敌对生物，或最近那只由远转近         | 只报「出现」与「逼近」，「走开」不报；10 秒冷却                     |
| `living_near`             | 身边来了别的活物（主人以外的生物/玩家/女仆）     | 判据是「上一帧还没有」+ 同种 60 秒冷却 + 一帧最多说一种             |
| `shelter_change`          | 从露天走进遮蔽处，或反过来                       | 连续两次采样一致 + 20 秒冷却；下界末地不谈                          |
| `ground_change`           | 脚下换了种值得说的地（水/岩浆/火/雪/沙/耕地/冰） | 只认这几类（石头泥土草地之间换不说）+ 30 秒冷却，水/岩浆/火不受它挡 |

光照与坐标不进事件（光照只进按需查询，否则她在火把之间走动就会刷屏；坐标永不外发）。
六类里**只有 `threat_near` 算紧急**（当场 `trigger_proactive("")`），其余走「攒够几条」那套——
不然每一次散步都会变成一次生成。

本地这一层**首帧永远不出事件**（只建基线），所以重连、换监控对象、区块卸载再回来都不会喷一屏；
现状由全局那层的 `state_snapshot` 交代，这是设计上的分工而不是巧合。

### 按需查询

`maid_look_around`（无参数）→ 模组回 `maid_look_around_result`，插件翻成四句事实：
站位与脚下与光照 → 正前方命中了什么 → 主人多远、看不看得见 → 附近一圈的活物与方位。

- 方位是相对她**身体**朝向的八向；只有「正前方」那条射线用头部朝向。
- 她自己的位置、视线、光照与周围实体全在服务端只读得到，**不读主人视角**；
  协议里一律只给注册表 id（专用服务端只有英文名），中文表在插件侧。
- 不受 `perceptionEnabled` / `noticeEnabled` 影响：采样是「她自发注意」，查询是「她被问到」。
- 已知限制：**插件工具只在主聊天可用**（主动对话与剧本的 `scene_normal` 工具列表是冻结快照），
  所以按需查询只发生在玩家跟她说话那一轮；主动开口那一轮读得到旁白、调不了工具。

宿主侧这一期**零改动**：插件 `[[tools]]` 早已授权给 default 角色组、也进得了 Tool RAG 的候选池，
`add_prompt_line` 与 `trigger_proactive("")` 都是现成的。`docs/plugin-dev-guide.md` 同样不用改
（本次全是既有能力的组合：多一条 `[[tools]]`、`_format_event` 多几个分支、`ws_request` 的既有超时纪律）。

## 代码分层整理（2026-10-16）

四期、五期连着加进来之后，两侧都出现了「一个文件什么都干」的苗头：模组的 `MaidActuator`
既改状态又读身边，`PerceptionSampler` 既做门控又读世界又管挨打去抖，两套判定里各抄了一份
帧外形与取整；插件侧则是一个 870 行的 `hooks.py`。这一轮按功能与接口重新分层。

### 模组侧的分层

按「碰不碰游戏」切三刀，判定一律留成纯逻辑（能脱开 Minecraft 跑单测）：

| 层                                                          | 干什么                                                             |
| ----------------------------------------------------------- | ------------------------------------------------------------------ |
| **改**：`MaidActuator`                                      | 让女仆动起来：寻路记忆、坐站睡、看向、找床与预检                   |
| **读**：`PerceptionReader` / `SurroundingsReader`           | 读全局那一层（维度群系天气血量）／读她身边那一小片（视线光照活物） |
| **判**：`PerceptionDiff` / `SurroundingsDiff` / `ActionRun` | 上一帧 + 这一帧 → 该不该报；一次动作的推进与收尾                   |

新抽出来的几件共用件：

| 文件                      | 谁在用                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------- |
| `game/EventFrames.java`   | 两套判定共用的帧外形（`event_type` + `maid_id`）与取整（原来是各抄一份）           |
| `game/GroundKind.java`    | 「脚下这块地值不值得说」的白名单，读快照与判定共用，协议 token 不会走岔            |
| `game/KeyedCooldown.java` | 按种类记冷静期（牧场里的一只只羊），带最久未提淘汰                                 |
| `game/HurtReporter.java`  | 挨打的去抖与上报，从 `PerceptionSampler` 里搬出来                                  |
| `PerceptionSampler`       | 只剩门控与节流：谁在听、多久采一次、按顺序问两层                                   |
| `MaidQueries`             | 多两条查女仆的公共入口（`requested` / `missingReason`），四个 handler 不再各写一套 |

### 插件侧：宿主支持多文件

插件脚本现在可以 `import` **同目录**的兄弟模块（`crates/ling-chat-plugins/src/python_backend.rs`
的导入钩子）。为什么要在宿主里做这件事：那个嵌入式解释器**没有任何文件系统能力**——冻结
标准库里没有 `os`/`nt`/`posix`/`_os`，`_io.open` 在调用时就报「Couldn't get FileIO」，
常规的文件查找器（`PathFinder`）既没装上、装上了也读不了文件，所以 `sys.path` 是形同虚设的。
读源码这件事于是由宿主代劳（`_read_plugin_source` 只认插件目录下 `<名字>.py`），插件只多拿到
「执行同目录某个文件」这一件事，仍然碰不到文件系统。面向插件作者的说明在
`docs/plugin-dev-guide.md`「拆成多个文件」。

### 插件侧：按功能拆成五个文件

`hooks.py` 曾是一个 870 行的文件：四个入口、十几张中文表、十四类事件的措辞、六个工具
挤在一起。现在按「谁跟谁一组」拆开，入口仍是 manifest 里声明的那几个文件：

| 文件         | 管什么                                             | 大约   |
| ------------ | -------------------------------------------------- | ------ |
| `hooks.py`   | 生命周期（启动 / 连接 / 某句上屏）与游戏事件的落地 | 225 行 |
| `bridge.py`  | 与模组的通道：连没连上、是哪只女仆、收发帧、读配置 | 106 行 |
| `wording.py` | 注册表 id、枚举串、数字 → 中文（表都在这里）       | 268 行 |
| `events.py`  | 一类事件 → 一句旁白（`FORMATTERS` 一行登记一类）   | 210 行 |
| `tools.py`   | 六个工具的入口（manifest 的 `[[tools]]` 指向它）   | 171 行 |

两处顺带的变化：

- **事件措辞从 if 链改成登记表**：加一类事件 = 写一个函数 + `FORMATTERS` 一行（紧急的再进
  `URGENT`），不必再在一个 14 分支的链子里找位置。行为逐字保留。
- **「连上了没、是哪只女仆、发一条帧」收进 `bridge.py`**：原先这三件事的样板在工具、上屏、
  绑定三处各写一遍（连不上、问不到女仆、没人应答三种说法也各写一遍），现在只有一份。

## 身边感知的改法修订（2026-10-16 夜，真机跑过一晚之后）

五期的六类事件按「边沿触发 + 分档 + 冷静期」实现得很克制，但**放进台词表就成了另一回事**：
一个晚上（16:27~16:37）攒下 34 条 `［MC 事件］` 旁白，其中 31 条是身边那一层——附近有村民、
附近有蝙蝠、玩家又出现在你能看到的地方、你走进了有遮挡的地方……她自己也在不停为这些开口，
十来个回合里几乎每隔一句就是「又有谁靠过来了」。信息不是错的，是**不该进历史**：玩家问的是
别的事，模型却每轮都要读一遍那片牧场。

改成**按需携带**：

| 改前                                    | 改后                                                        |
| --------------------------------------- | ----------------------------------------------------------- |
| 身边六类各自推事件 → 各写一条永久旁白   | 只在玩家开口那一刻现取一份快照，附在那句话后面带一次        |
| 紧急的那条当场开口、其余攒够几条开口    | 只有 `threat_near` 还写旁白并当场开口，其余不再触发任何生成 |
| 她「知道周围有什么」＝ 台词表里有这些行 | 她「知道周围有什么」＝ 那句话后面跟着「（你此刻：…）」      |

- 携带那句由 `tools.carry_text` 生成（与 `maid_look_around` 共用同一次查询与同一个
  `_owner_phrase`），只有脚下、头顶、玩家远近、附近活物四件事；正前方那一眼与光照留给工具
  ——玩家问起来才需要那么细。超时 1.5 秒，取不到就不带，玩家的话照常送。
- 那五类（`player_proximity_change` / `player_sight_change` / `living_near` / `shelter_change`
  / `ground_change`）在 `events.py` 的 `FORMATTERS` 里**不登记**了，于是自动落进「认不出的
  event_type 一律不出声」那条既有约定——**模组照推不误，插件不再理会**。这样这次修复只靠
  重启 LingChat 就生效，不必等换 jar。
- `threat_near` 保留原样（写旁白 + 当场开口）：它是唯一「得当场叫醒她」的观察，挨一下打有
  `maid_hurt` 兜着，但被苦力怕摸到跟前这种事不能等到玩家下次说话才知道。

顺带改掉的第二件事：**玩家在 MC 里说的话不再带 MC 账号名**。原先送进对话的是
`［Minecraft］玩家（NoiQing_Ling）说：…`，模型那一晚最后一句台词里凭空写了一句
`user［Minecraft］玩家说：这周围好多僵尸啊`（外加一个 `(NoiQing_Ling)`，被解析成了动作）——
它照着那个「谁在说」的形状**替玩家续写了下一句**（这正是系统提示里「输出边界铁律」第 2 条
明令禁止的）。模型该看到的玩家只有一个名字，就是 LingChat 设置里那个；MC 账号名是外部产物，
写进去只会多出个「第三个人」。现在只有「配置里填了 MC 用户名、而说话的不是他」时才点名。
提示行也重写了（多交代一句「（你此刻：…）」是什么），并且**幂等改成按内容判**——写法变了
老存档要重新交代一遍，否则模型一直按旧规矩理解那几个标记。

**待定**：模组那头还在算、还在推这五类帧（`noticeEnabled` 默认开着），插件已经不理它们了；
而 `threat_near` 和它们共用同一个 `noticeEnabled` 开关，关掉会连威胁一起关掉。要不要把五类
从模组里摘掉、把威胁从这个开关里拆出来，等真机验收之后再定——模组现在已随仓库入库
（`extension/maid_mod/`），删掉的代码能从历史里找回，但这一步仍值得单独想清楚再动。

### 第二轮：话里不带数字，怪物两分钟只提一次（2026-10-16 更晚）

上面那版跑起来之后，新的毛病是**她照着旁白复述数字**：模型看到「大约 10.5 格」「掉了 0.2 点血」
「光照 12」，就会把这些念进台词里。数字是给程序看的，不是给她说的。于是全面改说法：

| 原来                                                  | 现在                                 |
| ----------------------------------------------------- | ------------------------------------ |
| 「有僵尸靠过来了，大约 6.2 格，在你左前方。」         | 「有僵尸靠过来了。」                 |
| 「附近有 2 个活物：右前方 10.4 格的史莱姆」           | 「附近有近处的史莱姆」               |
| 「你被僵尸打了，一共掉了 0.2 点血，现在是 39.8/40。」 | 「你被僵尸打了，受了点轻伤。」       |
| 「你的血量只剩 3/40，快撑不住了。」                   | 「你伤得很重，再挨一下就撑不住了。」 |
| 「玩家就在你 3.4 格以内，你看得见他。」               | 「玩家就在你身边。」                 |
| 「光照 12」                                           | 不再提                               |

- **方位一概不说**（2026-10-16 再改一轮）：模型会照着旁白复述「左前方有僵尸，离我不远」，
  而这些细节对玩家没用——她该知道的只是「有危险在靠近」。所以威胁那条只剩「有 X 靠过来了」，
  活物清单只说「近处的僵尸」这类。`wording.DIRECTION_NAMES` / `direction_text` 随之删掉，
  模组仍然在协议里给 `direction`，插件不再读它。**唯一保留方向的**是工具那句「正前方 X 是…」
  ——那是「她正对着什么」，本来就是这一问的答案。
- **距离只给「近/中/远」**（`wording.nearness`，分界 5 格与 10 格，对着模组的感知半径定）。
- **伤势只给档位**（`events._hurt_phrase`）：一点以内「受了点轻伤」，五点上下「被打得有点疼」，
  十点上下「挨了几下重的」，再多「被打得很惨」。连挨几下仍然说「连着挨了几下」。
- **血量数字整条从 `state_snapshot` 里拿掉**：低血量另有 `low_health` 那条专门交代，而且
  模组那一层在接上后的下一次采样就会判（`maidLow` 初值是假，不靠基线帧）。两处各写一套阈值
  只会互相打架。
- **「看不看得见玩家」换成「在不在她身边三十格内」**（`tools.OWNER_NEAR`）。视线那条会让模型
  去编「我看见你了」，而主人有没有走远才是要紧的；那条射线仍然只用在「正前方挡着什么」。
  模组的 `player_proximity_change` / `player_sight_change` 两类帧照旧不理会。

**怪物的频率也收紧了**：模组侧 `SurroundingsDiff.THREAT_COOLDOWN_TICKS` 从 10 秒提到 **2 分钟**
（2400 tick）。报过一次「有东西靠过来了」之后，这两分钟里新出现的、又走近的都不再另记一条——
夜里围上来一群僵尸，玩家要的是知道有危险，不是每一只都来一句。这期间她身边站着谁有两处补位：

1. 玩家开口时随消息带一句（上面那条路）；
2. **出事（挨打、血量告急、动作收尾）那条旁白后面缀一句眼前的活物**
   （`hooks._creature_text` → `tools.creature_text`）。这正是「因为别的事件触发主动对话时
   再感知一次周围」——插件没有时钟也存不下状态，那个 2 分钟防抖只能放在模组里。

这一条要**换 jar**才生效（`THREAT_COOLDOWN_TICKS` 在模组侧）；插件那部分仍然是重启 LingChat 即可。

| ------------ | ------------------------------------------------------------------------------------------- |
| `wording.py` | 新增 `nearness` / `nearness_place`；`sighting` 不带格数也不带方位；删掉 `number` 与方位表   |

### 第三轮：附近死亡走事件，动手的是谁也不念账号名（2026-10-16 又晚一点）

到这儿为止，「事故」一侧只有两条监听器（说话、挨打），其余全是轮询。轮询答不出**因果**：
村民被僵尸咬死那件事，快照差分最多能说「附近原来有村民，现在没有了」，说不出为什么——
真机上她是听玩家打字才知道的。所以补上第一条真正的「事故事件」：

- **`LivingDeathEvent` → `DeathReporter`**：附近（`noticeRadius` 之内）有生灵死了就报一条，
  带上死的**是什么**、**谁杀的**、以及环境伤害的**伤害类型**。`LivingDeathEvent` 是全世界
  每次死亡都发，所以头一件事是认位置，半径外的直接丢。
- 同一场屠杀会连着死好几只（爆炸、僵尸围村），所以**只报第一条**，之后安静 10 秒。挨打那条
  用的是「等这一波停了再合成一条」，这里用不了：死掉的东西不会复原，合并只会把「谁死了」
  搅成一锅粥。
- **玩家死在旁边是紧急的**（当场请她开口），其余生灵死了只记旁白，跟着「攒够几条」那套走。
- 被监控的那只女仆自己死了**不走这里**，现在也不报——她的死牵着重生、身体回到哪、感知基线
  重建，得单独想清楚。这是一处已知空缺。

顺手修掉一处会漏账号名的口子：**「谁动的手」不再靠 Python 拿配置里的用户名字去比对**。
模组本来就知道她主人是谁，所以帧里直接带 `attacker_owner`（是不是她主人干的）与
`attacker_type`（生物注册表 id），插件据此说「玩家」「僵尸」；没有配置也能说对，账号名也不再
出现在上下文里。`maid_hurt` 那两条跟着一起改了（以前没配置时会写成「你被 NoiQing_Ling 打了」，
现在生物一律说中文名，别的玩家说「别的玩家」）。取谁动手的那套逻辑（箭与火球要退到发射者）
抽成了一个 `Attackers`，两个上报器共用。

**2026-10-17 修正**：`creature_death` 原先只带 `attacker_owner`，而插件把它说成了「被你杀了」——
「你」是女仆，主人杀的却记在她头上（真机：玩家杀了两只羊，她困惑了一整天「我根本没打算动手」）。
现在帧里多带一个 `attacker_maid`（是不是她自己动的手），插件按 `attacker_maid` → 「被你杀了」、
`attacker_owner` → 「被玩家杀了」、`attacker_type` → 「被僵尸杀了」、`attacker` → 「被别的玩家
杀了」的顺序说。顺序是硬要求：她自己与生物都带显示名，先认名字就会把一切杀手都说成玩家。

伤势的说法顺手改成了不预设「是被打的」：摔伤、淹死、烧死也走 `maid_hurt` 这一条，
「你从高处摔了下来，被打得有点疼」是说不通的，现在是「伤得有点疼」。

## 事故与状态：两条腿各管一段（2026-10-16 议定）

现在模组挂的监听器只有四条（开服、停服、每 tick、玩家说话）加两条「事故」：
`LivingDamageEvent`（挨打）与 `LivingDeathEvent`（附近死亡）。其余一切——换群系、天黑下雨、
走没走进遮蔽、主人远没远、身边有什么——都是**轮询**：每 5 秒读一份世界状态，跟上一帧比，
只报边沿。

有人提过另一种做法：挂上所有事件，凡发生在女仆附近的就记下来。它的好处是真的——**因果**
（谁把谁弄死了，轮询永远说不清）、**零延迟**、**无采样盲区**（5 秒间隔里发生又复原的事轮询
根本看不见：苦力怕摸进来炸了、羊被雷劈了）。但它是**补充**，不是替代：

- 它答不出**当前状态**（「你周围有什么」「主人在不在」），那必须有世界镜像，也就是轮询这一层；
- 它不解决**噪音**，只放大素材——刷怪塔每秒几十个实体 join、连锁挖矿一次几十个方块事件，
  每一条都还得再过一遍同一套「就地过滤 → 合并 → 分档 → 冷静期」（`HurtReporter` 与
  `SurroundingsDiff` 那两分钟防抖就是模板）；
- NeoForge 没有「监听一切」的入口，挂得越多，升级要改的地方越多。

所以规矩定成：**事件只管「事故」**（有因果、有时间点、攒不回来的事），状态一律靠轮询；
真要再加事件，就照 `DeathReporter` 的样子来——认位置、只报第一条、之后安静一段。

### 玩家屏幕（她能不能看到玩家看到的东西）

**2026-10-17 落地：能，而且不用客户端模组、也不用动服务端模组——画面由 LingChat 自己抓。**

起因是用户提了一个文字说不清的场景：「我给女仆建了个爱心或者房子想给他看看」。服务端能给的是
「脚下是草方块、附近有只羊」，而**形状**这类信息它永远说不出来。核过之后发现当时否掉这条路
的三条理由全都站不住：

| 当时说的                                       | 实际情况                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「模组是纯服务端的，服务端没有画面，出图很贵」 | 出图不必经过游戏：**LingChat 自己就有窗口截图能力**（`tauri-plugin-screenshots`）。`enumerate_all_windows()` 列出**所有进程**的顶层窗口（注释写明故意不按 PID 过滤），`capture_own_window(hwnd)` 也不校验窗口归属——抓游戏窗口是现成能力                                                                       |
| 「要给宿主加一个把图片随消息送进对话的能力」   | 早就通了：`send_chat_message(text, screenshot_base64)` 已支持，聊天窗那个截图按钮走的就是它。插件这条路上唯一的缺口是一个写死的 `None`                                                                                                                                                                        |
| 「研究结论说文本优于画面，图的边际价值不高」   | **读反了。** VoyagerVision 给 Voyager 加上截图之后，解锁的正是**建造类**任务（50 轮里平均搭出 2.75 个结构，超平坦地形成功率 48%）——「看一眼就知道你搭了什么形状」恰好是视觉唯一无可替代的场景；它说的变差是**采资源**那一类。Cohen 那篇是 2023 年的行为克隆工作，评测口径是任务成功率，既过时、场景也不是陪玩 |

做法（三层，职责照旧）：

1. **模组不参与。** 画面不来自游戏进程，来自玩家的屏幕，所以 `extension/maid_mod/` 一行没动。
2. **插件只决定「看哪个窗口」**：`maid_see_screen` 工具 → `capture_screen(window="Minecraft")`。
   `screen_window` 配置项给关键词（标题或进程名命中即可，默认 `Minecraft`）。
3. **宿主负责抓、压、送**：找窗口 → `capture_own_window` → 缩到长边 1024 编 JPEG（约一千 token）。
   图顺着**工具结果附图**协议（`{"image": {"data_url", "hint"}}`）交回去，宿主的工具环从结果里
   把它摘出来，单起一条消息附在本轮请求里——tool 角色本身带不了图。

**为什么是「工具」而不是「每条发言都带一张」**：一开始做的是后者，用户否掉了——每次发言一张
既是钱也是噪音，而且多数发言根本不需要看图。改成工具之后，什么时候看由模型按对话判断
（「你看我搭的爱心」→ 调工具），代价只花在真要看的那些轮。代价是模型可能想不起来调——这正是
「工具推荐」那条通用能力要解决的问题（见 `docs/function_call/tool_rag.md`）。

**抓失败的三条退路都回整屏**（那时玩家多半正开着游戏，整屏就是游戏画面）：没找到那个窗口、
抓取失败、抓回来的图不像一张画面。第三条专门为「窗口最小化」设的：最小化（含枚举与抓取之间的
时间差）时 PrintWindow 只能给回标题栏那一小条，甚至几像素——那种图给了模型只会让它胡说。
判据是**窗口短边小于 200 像素**，或**整张图一个颜色**（独显全屏的游戏，PrintWindow 常常只给回黑图）。

**已知取舍**：

- 图片只在这一轮请求里（工具环把它从记忆副本里摘掉），不写台词历史、不进长期记忆；
  她要在下一轮还记得，得自己说出来。
- 原生识图没开时 `capture_screen` 直接失败并说明原因：抓了也送不进对话。
- 只抓主屏（`GetSystemMetrics(SM_CXSCREEN)` 那套的老限制）；多显示器下副屏上的游戏抓不到。
- 屏幕里若叠着 LingChat 自己的窗口，模型会在图里看到自己——工具结果附图时那句 `hint`
  点了一句「图里如果有聊天窗口，那是你自己在的那扇窗，不用管它」。
- 「玩家看向哪、视野里有什么」那条**服务端算法仍可做且仍没做**：它给的是带名字的结构化信息
  （他准星对着箱子、视野里有村民），截图给不了这个。两者互补，不是替代。

## 七期：物品与投喂（2026-10-17）

玩家给女仆东西有四条路，可观察性差别很大，这一期把能看见的都看见：

| 玩家做的事                     | 游戏里实际发生什么                                        | 怎么观察                                                         |
| ------------------------------ | --------------------------------------------------------- | ---------------------------------------------------------------- |
| 潜行 + 右键任意食物            | 普通食物原本只开界面；本模组补成「真吃」一个              | 我们自己的 `InteractMaidEvent` → `item_fed`                      |
| 潜行 + 右键金苹果 / 附魔金苹果 | 车万女仆 `ApplyGoldenAppleEvent` → `maid.eat`（成就照旧） | `HIGHEST` 先留一份副本，`MaidAfterEatEvent` 确认真吃了再补记     |
| 把物品丢在地上                 | 进世界；她开了拾物模式且背包有空位才会捡                  | `ItemTossEvent` → `item_gift`；`MaidPickupEvent` → `item_pickup` |
| 右键开界面后把物品放进她的背包 | 直接进背包，没有任何事件                                  | 采样前后比一次 → `item_received`                                 |

几条实现上的硬知识：

- `InteractMaidEvent` 在客户端与服务端各发一次，必须判 `event.getWorld().isClientSide()`。
- 事件优先级：NORMAL 是车万女仆自带的交互（背包、药水、金苹果）；普通食物喂食挂在 `HIGHEST`（2026-10-18 凌晨从 `LOW` 提上来），抢在切坐姿（`LOWEST`）与别的附属模组之前取消，所以拿着食物潜行出手是喂饭而不是坐下；金苹果的副本也留在 `HIGHEST`（吃掉之后那份就空了，事后认不出来），补记改挂在 `MaidAfterEatEvent`（2026-10-18 第三轮，确认她真的吃了；交互被别的模组取消时不会误报）。空手与被抱着（成为玩家乘客）时一律不碰。
- 背包差分要扣掉捡取事件已经报过的账，否则同一件事说两遍；捡的是不是主人丢的，靠 `ItemEntity.getOwner()`（Q 丢与界面外拖拽都会记 thrower）。
- 丢东西的半径沿用 `noticeRadius`；首帧、换背包（格子数变化）、关掉 `noticeEnabled` 都只重建基线，不出事件。
- 帧里只给注册表 id 与数量；中文物品名在插件的 `ITEM_NAMES`，方块表兜底，认不出退回 id 后半段。

不做什么：Shift+右键直接塞背包（只检测背包变化，不改交互）、喂食加好感度（只按营养值回血）、地面躺下（仍暂缓）。

## 主动对话的并发与事件排队（2026-10-17 修复）

真机战斗里暴露的问题：女仆反复挨打 → `maid_hurt` 每一下都算紧急 → 插件每次都 `trigger_proactive`；宿主对每个请求各起一个任务等生成锁，于是上一轮还没播完，后台已经排了一串。它们逐个生成，台词表与记忆里混进了多轮重复的悔恨与担心，模型也被一屏「你挨了打」喂得反复复述。

四处改动，各管一段：

1. **宿主：生成期间的提示行排队。** `add_prompt_line` 在生成锁被占时不再直接写，而是进 `GameStatus` 的待写队列（上限 200 条），返回 `{ok:true, queued:true}`；下一轮开头（用户发言或主动对话，拿到生成锁之后）按顺序补进台词表。生成期间直接写会与流式任务按位置回填的助手台词抢行号，是「记忆被搅在一起」的根源之一。
2. **宿主：插件主动对话只攒一条。** `ProactiveSystem` 新增 `plugin_request` 单槽 + `plugin_last_delivery` 冷却（20 秒）+ 队列 TTL（2 分钟）。短时间连发只保留最早一条，投出去后要冷却；前台空闲通知或 30 秒轮询时尝试投放。
3. **前端：空闲判据包含台词播放。** `useCanDeliver` 增加 `currentStatus === "input"`：生成中、台词还没播完、等玩家点继续都不算可投放。宿主在 `can_deliver` 翻成 true 时立刻尝试投放排队的请求，所以「这一轮说完再说下一轮」是事件驱动，不必干等轮询。
4. **模组：挨打上报去抖加下限。** `HurtReporter` 在两次上报之间至少安静 5 秒（`PUSH_GAP_TICKS`），伤害与次数照常累计。战斗中事件从「每十来 tick 一条」降到「每 5 秒一条」。

效果：**同一时刻最多一轮在生成、最多一条在排队；两次插件主动对话至少隔 20 秒。** 事件仍然会写进台词表（排队只是保证它们出现在下一轮开头，而不是插进正在生成的这一轮），所以模型不会漏看。

## 事件合并与消息形状（2026-10-17 晚间）

真机上另一处观感问题：同一刻发生的三件事写成三行旁白（「不远处的羊被你杀了」「玩家往你脚边丢下了切制砂岩」「不远处的羊被你杀了」），玩家一句话后面跟着一屏几乎同义的记录，模型也容易把同一批事件念成好几句。

- **接连发生的事件并进同一行。** 插件写完一条旁白后立刻回读最后两行：上一行仍是自己写的 `［MC 事件］…`，就说明这中间玩家与角色都没说过话，于是用 `edit_context` 把它改写成「…；…」（前一段结尾的句号让给分隔符）。攒到 6 件或 300 字就另起一行。`edit_context` 在生成中会被宿主拒绝，所以合并不可能与流式写入抢行号；并发下如果行号已被另一次调用合并过，就宁可多留一行。
- **宿主补写时也合并。** 生成期间排队的那几条旁白，`GameStatus::queue_prompt_line` 直接把连着的 narrator 用换行接成一行（上限 600 字），下一轮开头作为一条写进台词表。插件侧读回时把「换行 + 重复标记」归一成「；」分隔的同一形状，所以两种来源合并出来的行长得一样。
- **「攒够几条」改成「攒够几件」。** 合并之后行数不再等于事件数，`_quiet_event_run` 按行内「；」分段计数；判定从「至少 count」改成「刚好 count」——到量请过一次口之后，后面每多一件不再重复催。
- **玩家在游戏里说的话不再带标记。** 送进对话的就是原样一句，宿主按玩家行补上 LingChat 的用户名（「用户酱: 你好」），和输入框里发的一句完全同形。多人服里说话的不是她主人时，仍然点名前缀（「某某说：…」）。`ENTRY_HINT` 相应重写（幂等按内容判，老存档下次连上会重新交代一遍）。
- **死因说清是谁动的手。** `creature_death` 多带 `attacker_maid`，插件按「你 → 玩家 → 生物 → 别的玩家 → 环境」的顺序说，玩家杀的羊不再记成「被你杀了」（细节见第三轮那节的 2026-10-17 修正）。

## Carry On 与成就（2026-10-17）

**被抱起来。** Carry On 抱人时会把实体从世界里摘掉（`RemovalReason.UNLOADED_WITH_PLAYER`），完整 NBT 存在玩家身上；放下时按原 NBT 重建，UUID 保留。所以：

- 被抱着的那段时间 `findMaidById` 查不到她，感知会当成「她不在」清基线；放下后照常重推 `state_snapshot`，这是设计好的「我丢线了」信号。
- 新事件 `maid_carried` / `maid_dropped`。**2026-10-18 起主路径改成 Carry On 自己的事件**：抱起听 `EntityPickupEvent`（在实体被移出世界之前触发），放回听 `EntityJoinLevelEvent`；事件挂不上（Carry On 版本对不上）时才退回每 tick 翻玩家 carry NBT 的 UUID 扫描。真机反馈过「抱起来不触发感知」，只靠轮询在部分环境里不可靠，两条路并用。
- Carry On 是**可选依赖**：`compileOnly` 编译、单独一个 `CarryOnPresent` 判断装没装、真正的调用隔在 `CarryOnBridge` 里；`CarryOnEvents` 只在已加载时注册，注册失败被 `try/catch` 兜住。没装时那些类不会被加载，桥接其余功能照常。
- 被抱着的现实限制：聊天气泡、动作、「看一眼周围」都要实体在世界上，这段空档用不了；放下来就好。

**跟随行为给长任务让路（2026-10-18）。** 车万女仆的 `MaidNonHomeRange`（默认 8）在实体创建时写进 `RESTRICT_RADIUS`；跟随模式下超过「半径 + 2」就把她**传送**回主人身边，正在挖的方块、正在追的目标全断。第一版想直接把 `RESTRICT_RADIUS` 放宽到 30，但拾物、找床、找餐桌、跟随全都读同一个字段，副作用比问题还大。

现在的做法是**不动半径**：用一个很小的服务端 mixin（`MaidFollowOwnerTaskMixin`）在「她手上有活 + 主人已经超出原版回头线（半径 - 2）」时取消 `MaidFollowOwnerTask.start`——攻击、挖方块、走过去/躺床，以及她自己界面里选的非空闲工作模式（农场、钓鱼……）都算；主人就在旁边时照常跟随，活干完或切回空闲后自动恢复。传送与「走回主人」都发生在那个方法里，取消它既不会清掉控制器写的 `WALK_TARGET`，也不影响任何别的范围。于是拾物、找床、找餐桌、跟随距离全部保持车万女仆原版。

配套改了一处判定：`maid_attack` 原先在跟随模式下要求目标离**主人**不超过「半径 + 2」，那是为了防传送；现在追打期间传送被拦住了，这条限制去掉，只保留居家模式的活动范围检查。找目标仍然看 32 格。

这是全项目唯一一处 mixin，目标类与 `start` 方法签名都对着 TLM 1.5.3 的 jar 核过；TLM 升级到改了该方法时启动日志里会有 mixin 注入失败，届时再修一版。

**玩家的成就。** 监听 NeoForge 的 `AdvancementEarnEvent`，只报她主人拿到的、且有展示信息的条目（`advancements` 数据里没有 `display` 的配方解锁这类自动跳过）。帧里给注册表 id、游戏内标题、`task` / `goal` / `challenge` 三档。中文名在插件的 `ADVANCEMENT_NAMES`：原版 127 条从游戏自带 `zh_cn` 语言文件生成，模组加的用游戏内标题，再不行退回 id 后半段。挑战另说一句「玩家完成了挑战…」。

两条都算**紧急事件**（当场请她开口），但都不再顺手补一句「你周围有什么」——收到东西、被抱起来、拿到成就都不是「出事」，抱起来时她甚至不在世界里。插件侧把这件事收成一张 `SNAPSHOT_EVENTS` 白名单。

## 工作模式（2026-10-17 晚）

玩家叫角色「去种地」「去钓鱼」时，她此前只能口头答应——她动不了自己的工作模式。现在有 `maid_set_task` 工具：插件把中文名归一成注册表 id，模组按 `TaskManager` 切她的任务。

- **切的是车万女仆自己的任务**，她的界面、存档、日程表跟玩家手点出来的一模一样，模组这侧不留副本。有没有这个模式由 `TaskManager` 回答，**旁人模组加进来的任务也能切**；插件那张 `TASK_NAMES` 只负责把「种菜」「待命」这类说法收拢成 id，不构成白名单（带命名空间的写法原样放行）。
- **切换成功不等于她此刻在干活**：日程表不在工作时段要等时段；跟随状态有活时跟随行为会让路（见「长任务与跟随」），她不会主动跟着主人走，主人走远也不打断活。回执里带 `work_time` 与 `home_mode`，插件把话说全（「现在是她的休息时间，到了工作时间才会去干」）。居家/跟随是她自己的设置，插件不替玩家改，只如实转达。
- **缺工具也照样切**：车万女仆的 `onFunctionCallSwitch` 会把背包里的锄头、剪刀、钓竿拿到她手上；拿不到就回 `MISSING_REQUIRED_ITEM`，插件说一句「得先给她」。
- **换工作前先把插件动作收掉**：动作控制器每 tick 写 `WALK_TARGET`，与工作模式自己的寻路互相顶；换工作时把没做完的动作按 `cancelled` 收掉（仍会推一条 `action_done`），坐着或睡着的先叫起来（`stood_up`）。
- **留一笔旁白**：真的换了模式时模组广播 `maid_task_change`，插件记「你换成了工作模式「农场」。」——工具回执只在那一轮上下文里，过一会儿她还得知道自己现在在干什么。中文名由插件给（22 条 TLM 自带模式 + 常见同义词），模组只给 id 与英文摘要。
- **玩家在女仆界面里手动改模式不会通知她**：那条路没有事件可挂，`maid_task_change` 只覆盖这个工具切的那一次。

## 指定攻击目标（2026-10-17 晚）

`maid_attack`：玩家说「去打那只僵尸」「打我一下」，她真的会去。目标由插件翻成 `owner` / `hostile` / `animal` / 实体注册表 id，模组找离她最近的那一只。

- **故意不走车万女仆的 `canAttack` 白名单**：它的规则里玩家、村民、有主的宠物都不打；这里连主人自己都能点名，是玩家明确要的玩法。仍排除盔甲架与她自己的实体。
- **自己驱动，不复用她的攻击 AI**（2026-10-17 真机回来改的）：第一版是把目标写进 `ATTACK_TARGET`、顺手切到攻击模式，结果游戏里毫无动静。原因是车万女仆的攻击行为只在「WORK 日程 + 攻击模式」下才跑，而且 `StopAttackingIfTargetInvalid` 用居家/跟随模式算有效范围（跟随模式下目标必须离**主人** 8 格以内），稍远就把目标清掉。现在由 `MaidAttackController` 每 tick 写 `WALK_TARGET` 追过去、贴身之后直接 `doHurtTarget`，出手间隔按攻击速度算——跟她的作息、工作模式都无关。
- **武器顺手换**：背包里有带 `ATTACK_DAMAGE` 的东西就换到手上（与她的攻击模式同一口径）；没有就空手打（1 点伤害），回执里 `weapon=false`，插件说明伤害很低。
- **范围**：找目标看 32 格。居家模式下目标要在活动范围里；跟随模式不再限制「主人到目标」的距离——追打期间跟随行为的传送被 `LongTaskGuard` 拦住了（见上），打完收工后跟随恢复。
- **力度分两档**：`fight`（默认）追着打到对方倒下；`light` 只出一手就收手——那一下不走 `doHurtTarget`（按武器算，一把好刀一下就能打掉大半条命），固定 1 点伤害、不换武器。真机上「打我一下」直接把人追着打死了，所以「轻轻」必须由玩家明说。
- **收工**：目标死了、被新指令打断、或追满 30 秒就停。打死了由死亡旁白（`creature_death` 带 `attacker_maid`）交代，工具回执不重复，只写「这个工具只下达攻击指令，目标还没有倒下」，免得模型替目标收尸。

## 挖方块（2026-10-17 深夜）

`maid_mine`：玩家说「把这块挖了」「挖十块石头」，她走过去把方块挖掉。参考了车万女仆的三个挖矿附属（MaidTask、Maid Mining、LMA）与 Baritone 的 builder，最后没有采用它们的**任务模式**（把挖矿注册成 22 个任务之一，让她按日程自己去挖），而是沿用攻击的做法：一次指令、一个控制器、做完就收。

- **为什么不做成工作模式**：挖矿附属的模式是「围着活动范围自动找矿、挖隧道过去」，要自己写 BFS 寻路、目标记忆与一整套行为优先级，还得和她的日程、工作模式抢 brain；这一期要的是「玩家指哪块，她挖哪块」，工作量差一个量级。工作模式的版本留作以后（真要做，MaidTask 的 `IMaidBlockDestroyTask` 是现成参考）。
- **目标两种**：`looked`（玩家准星指着的方向）或方块注册表 id（插件把「石头」「铁矿」翻成 id）。`count` 默认 1、上限 64。
- **玩家指哪片就在哪片挖（2026-10-18 真机修正）**：原版按「离她最近」挑块，玩家指着 A 区、她跑去 B 区，不指就只会搜她自己脚下。现在准星射线放宽到 32 格、落点当作区域中心：写了方块名先在这片 8 格内找，找到就整单都只在这片挖；`looked` 先挖落点那块、再在这片补够。准星没指着、或这片里没有目标，才退回以她为中心 24 格找。协议仍不出现坐标，回执也不带方位与「是哪一棵」。
- **按族找方块（2026-10-18）**：`target` 接受方块标签（`#minecraft:logs`），插件把「木头 / 原木 / 树干」翻成它，于是云杉林、白桦林都能砍；普通矿石 id 自动带上深层变体（`iron_ore` 也认 `deepslate_iron_ore`），地下不会再因为只剩深层矿而报「附近没有」。
- **「看一眼周围」带方块清单（2026-10-18）**：`maid_look_around` 的回帧新增 `blocks`：附近能挖的方块种类（注册表 id、按最近距离排序、最多 12 种、不列空气/液体/花草/基岩），玩家准星指着某处时以落点为中心、否则以她为中心，扫描范围与挖掘同口径（水平 24、竖直 8）。插件翻成「附近能挖的方块有云杉原木（minecraft:spruce_log）……」；模型看到实际 id 后再调 `maid_mine`，不必猜方块名。老模组不回这个字段时插件不替它说「没有」。
- **落脚点**：目标周围 5×5×5 里找站得下、够得着（眼到手 ≤ 5 格）、视线第一眼就是目标、并且 `canPathReach` 能走到的位置；找不到就当场拒绝 `unreachable`，不让她对着墙原地转。草、花这类没有碰撞体积的方块改用轮廓射线判视线。
- **进度按原版算**：正确工具 `速度 / 硬度 / 30`，用错工具或徒手 `/100`；硬度为负（基岩）挖不动；`destroyBlockProgress` 发裂纹，玩家看得见。工具从背包里挑挖这一块最快、且能挖出掉落的那个（只比较正确工具，不会拿剑去挖石头），方块要求正确工具而她没有时当场拒绝 `wrong_tool`。
- **掉落进背包**：走车万女仆的 `destroyBlock`（`canEntityDestroy` + NeoForge 的实体破坏事件），受保护的方块不挖；装不下才掉在地上。
- **异步收尾**：受理只代表开始挖，`maid_mine_done` 才代表挖穿/挖够/没挖成；工具回执只写「这个工具只表示开始挖了，方块还在原地」——和攻击那边是同一个教训。
- **互斥**：与动作、攻击、换工作模式共用一条寻路通道，新的顶掉旧的；顶掉时不补事件（与攻击一致）。

## 工具回执与事件时效（2026-10-18）

真机上一场战斗把三个问题摆到了一起，挨个修掉：

- **调用工具前说的话会丢（宿主）**：`genai` 适配器把带工具调用的 assistant 消息组成了「只有工具调用、没有正文」，模型在下一轮看不到自己刚说过的前导台词，于是重新开场、把同一件事再说一遍（真机表现为调完工具回来又「冲上去打猪了」）。现在正文与工具调用一起下发（`ContentPart::Text` 在前、`ToolCall` 在后）；Kimi-Code / Codex 两条适配器本来就是对的。记忆构建与 `CONTINUATION_PROMPT` 都没问题，问题只出在请求组装这一层。
- **事件要有时效（插件 + 宿主）**：`add_prompt_line` 新增 `ttl_seconds` / `key` / `severity`。带有效期的条目**不再立刻进台词表**，先留在宿主队列里，等角色真要开口那一刻再筛一遍：过期的直接丢弃。每类事件的有效期在插件 `events.EVENT_TTL`（捡东西 5 秒、受伤 60 秒、换地形 10 分钟）。同类事件（`maid_hurt`）用 `key` 合并，只留 `severity` 最大的一条——连着挨几下只记最重的那一次。排队条数由宿主回给插件，插件据此判「攒够几件了」（不再从台词表读）。这样第一轮台词还没念完时攒下的「捡起一块木头」不会在一分钟后混进对话。
- **工具描述只陈述能力边界（插件）**：不再写「会有旁白告诉你」「等消息」这种预告，改成「这个工具只负责攻击，不代表目标已经倒下」「只表示开始挖了，方块还在原地」。模型会照着工具结果对玩家说话，原来的措辞让它总爱补一句「等有结果了会告诉你」，人机感很重。入场提示里的同类句子一并改掉。

第二轮真机（2026-10-18 凌晨）又补了四处：

- **被抱起来才是紧急事件**：`maid_carried` 留在 `URGENT`，`maid_dropped` 退出——放下只是接着上一件事往下走，不必抢一次生成。
- **主动对话也能用插件工具**：插件工具注册时除了授权 default 角色组，也写进「主动对话」映射到的场景组（默认 `scene_normal`）。场景组是一份早先写死的工具快照，后来注册的插件工具不会自动进去，于是怪物靠近时 `tool_search` 只翻得到 `get_current_time`，`maid_attack` 也会被判 `tool_not_allowed`。禁用插件时两处授权一起收回。
- **`/查看记忆` 补上工具调用**：之前只打 role 与正文，历史里只剩孤零零的工具结果，看不出是谁发起的调用；现在每条 assistant 消息的 `tool_calls`（名字 + 参数）与 tool 消息的 `tool_call_id` 都会打出来。
- **喂食抢在最前面**：普通食物改为在 `InteractMaidEvent` 的 `HIGHEST` 当场吃掉并取消，切坐姿（TLM 的 `LOWEST`）与别的附属模组的右键逻辑都收不到这一下，潜行拿食物出手只会喂饭，不会顺带坐下；金苹果仍由 TLM 自己吃，只留副本事后补记。
- **看不见的活物只说声音**：附近实体里 `visible=false` 的不再逐条报「（被挡着）」，改为汇总成「附近能听到僵尸和蜘蛛的声音」（同类只念一次）；看得见的照旧按距离档报。隔墙知道具体是哪一只、离多远，读起来像透视，也不像她真有的感官。

第三轮真机（2026-10-18）：

- **喂食不再和 Carry On 抢手势**：空手不喂（空手右键在搬运模组那边是抱起/放下），玩家手里抱着任何东西、或者她被抱起来（成为玩家乘客）时也不喂、不取消交互。金苹果的补记从「事件被取消就记」改成「等她真的吃完（`MaidAfterEatEvent`）才记」，交互被别的模组截走、她没吃到时不会再误报 `item_fed`；待补记 20 tick 内没走到吃就作废。
- **她自己吃东西也有检测**：车万女仆的进食系统先 `startUsingItem`，完成时走 `LivingEntityUseItemEvent.Finish`（`getItem()` 是吃之前那份，认得出是什么；`MaidAfterEatEvent` 只给吃完剩下的，普通食物那里是空的）。这条推 `maid_ate`，与玩家喂食分开措辞，不算紧急，TTL 60 秒。
- **被抱着时不接受指挥**：动作、攻击、挖掘一律回 `maid_carried`；`MaidActuator.standUp` 对「玩家身上的乘客」直接不动，挖掘/追打控制器发现她被抱起来就收手。此前 `standUp` 会 `stopRiding` 把她从玩家身上拽下来，正好把 Carry On 的搬运数据拆散，表现就是「黏在手上放不下来」。
- **`maid_give_item`：女仆把背包里的东西交给玩家**：同步完成，不占动作槽。只从背包拿（她手上正用的工具不算），玩家须在同一维度且 8 格内；直接放进玩家背包、装不下掉在脚下。回执带 `count`（实际给了几件）与 `requested`（要了几件），给不足时插件说「她身上只有这么多」。
- **交物品要能看见背包**：真机上模型想交「玫瑰丛」，先猜 `rose bush`、再猜「玫瑰丛」，两次都在插件本地被名称表挡下，根本没问到游戏。现在三处补上：① `maid_look_around` 回帧新增 `backpack`（背包物品 id 与数量，最多 12 种），工具说明让模型不确定时先看它；② 英文短语按 id 归一（`rose bush` → `minecraft:rose_bush`）；③ 认不出的名字不再本地拒绝，照样发给模组，`bad_item` / `not_found` 回执带 `available`（同一份背包清单），模型同轮按 id 重试。

### 感知分层（2026-10-18）

真机症状：她在地表走，脚下洞里十几格的僵尸也算「身边有东西」，开口时还汇总成「附近能听到僵尸的声音」——旧实现是一个以她为中心的三维球（`noticeRadius` 12），看不见的活物也在球里，插件再把 `visible=false` 的翻译成声音。

现在把感知规则收成一处（`PerceptionProfiles` + `Surroundings.Profile`）：

| 档                                     | 看得见                                               | 看不见                | 上限 |
| -------------------------------------- | ---------------------------------------------------- | --------------------- | ---- |
| `auto`（周期采样、开口时顺手带的那份） | `max(noticeRadius, min(MaidWorkRange, 32))`，默认 12 | `heardRadius`，默认 6 | 3    |
| `query`（玩家明确问「你周围有什么」）  | 32                                                   | `heardRadius`，默认 6 | 3    |

- 「看得见」用无遮挡判定，不要求她面朝目标；看不见的只在听到半径内保留，插件说「听到…的声音」，不再说「靠过来了，你还没看到它」。
- 两档都只列最近 3 个（`Surroundings.NEARBY_LIMIT`），多的切掉并标 `truncated`。
- 自动档不再扫方块与背包：玩家每句话、每次受伤都会取一份 `auto` 快照，跟着扫 24×17×24 的方块是浪费；`blocks` / `backpack` 只在 `query` 里给。
- 被抱起 / 放下的旁白每种每个监控周期最多两条（`CarryReporter.MAX_REPORTS`），反复搬运不再每次写进台词表。
- 判定是纯逻辑（`Surroundings.eligible`），单测覆盖「看得见 12 格、看不见 6 格」的边界。

### 建筑（下一期，待定）

玩家的下一个需求是「让女仆建筑」。调研过的三条路：

| 来源                                         | 做法                                                                                     | 适不适合                                                                             |
| -------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Baritone builder                             | 读 `.schem` / `.litematic`，逐块比较世界与蓝图，寻路到可放置的位置，带材料时放、不对时拆 | 最完整，但它是客户端模组，蓝图解析与寻路都要在服务端重写一遍                         |
| MaidTask 的 `BuildHouseBehavior`             | 代码里写死一份小屋蓝图，凭空放方块，不耗材料、不管寻路                                   | 只能盖那一种小屋，且是创造模式语义                                                   |
| Minecraft Builder skill（mattzh72 / pofice） | 用 JS 或 Python 生成原版 `.nbt` 结构 / 直接改存档，预览后再放进世界                      | 适合**生成蓝图**，不适合实时指挥女仆：插件没有文件系统，模型也拿不到几万块方块的蓝图 |

倾向的分期：先做「读结构文件 + 从背包取材料 + 逐块放置」的 MVP（蓝图放服务器目录，玩家用 skill 或投影模组生成），再做「模型给一个很小的形状 DSL（墙/地板/坡屋顶）」，后者只够盖凉亭、不追求大建筑。两条路都要先解决「玩家怎么知道要什么材料」，这一期不做。

## 六期（暂缓）：自己补两个动作 —— 地面躺下、直接投喂

投喂已按七期的简化形态落地（潜行右键任意食物，只回血、不加好感度）；下面这节保留当时的调研结论，「直接投喂」里只剩好感度那半没做。地面躺下仍然暂缓。

四期做完整理源码时的结论：车万女仆的功能其实不少（女仆会自己去餐桌吃饭、可以喂金苹果、有工作餐与回血餐、有整套好感度），但它**不把这些暴露成外部能调的动作**——没有躺姿这种东西，也没有「喂一份」的入口。要加就得我们自己补一层控制。**两个都不需要改车万女仆的源码**，只是把它已有的内部机制当 API 用（`setPose`、`eat`、好感度的 `Type`）。

### 一、地面躺下

现状只有「睡床」（四期的 `lie_down`，走她的 `startSleeping`，白天会被日程叫醒）。

做法：`maid.setPose(Pose.SLEEPING)` 并**每 tick 保持**，同时冻结移动（清 `WALK_TARGET` / `PATH`、速度清零）。**躺姿渲染是白送的**：原版 `LivingEntityRenderer.setupRotations` 有 `Pose.SLEEPING` 分支，会把整个模型转成躺姿、方向取她当前朝向（不在床上时用 yaw 兜底），车万女仆的女仆渲染器继承它并调 `super`——床上怎么显示，地上就怎么显示，不用写客户端代码。

要处理的三件事：

- 水里 / 岩浆上会被原版强制切成游泳姿，所以受理时预检「脚下是实心方块、不在液体里」，中途泡进液体就自动起身；
- 挨打或恐慌时自动起身，否则她会带着躺姿滑出去；
- 跟随模式与随机走动会一直想让她走：我们是**每 tick 抢占**（写在她实体 tick 之后）。这是压制而不是她认可的状态，不如坐姿干净——坐姿是车万女仆自己的旗标，`canBrainMoving()` 直接为假。

**唯一的不确定项是造型**：模型是「站着的身子整体转 90°」，看着别扭的话就得自己写客户端渲染旋转，那才是真正贵的部分（+1~2 天，且要碰 client 侧）。所以先做服务端版，真机看一眼再决定要不要碰渲染。

落地形态：并进现有工具（`maid_lie_down` 加 `target: bed|ground`），不新增工具，`tool_search` 的菜单也不变长。

### 二、直接投喂

先记下调研结论——车万女仆里「喂」分三条路，可观察性差别很大：

| 玩家做的事                             | 游戏里实际发生什么                                             | 能不能观察到                                              |
| -------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------- |
| 潜行 + 右击，手里是金苹果 / 附魔金苹果 | `ApplyGoldenAppleEvent` → `maid.eat()`，她真的吃下去           | 能：`MaidAfterEatEvent`                                   |
| 手里拿普通食物右击她                   | **她不吃**，只会弹出女仆界面；食物是塞进她背包后到饭点她自己吃 | 只能看到「右击」这个动作（`InteractMaidEvent`），看不到吃 |
| 往野餐垫（餐桌）上放食物               | 进垫子的容器，到饭点她去吃                                     | 是方块交互，不是实体交互，要另挂 `RightClickBlock`        |

**「她真吃下去了」有一个权威钩子**：车万女仆的 `MaidAfterEatEvent`（`api/event/MaidAfterEatEvent`，从 `EntityMaid.eat()` 里 post，服务端触发）。玩家喂的金苹果、她自己在家/工作/回血餐时吃背包或餐桌里的东西（`IMaidMeal.onMaidEat` → `startUsingItem` → 用满时长 → `finishUsingItem` → `eat()`）都会走到它。它覆盖不到：偷吃方块（只加好感不消耗）、普通食物右击（没吃）、女仆喂玩家（那是玩家在吃）。

做法（照车万女仆自己的餐食逻辑抄，不自己发明）：

1. 取一份食物——默认取**玩家主手那份**（玩家刚给的就是手里这个，最可预期）；也支持指定物品 id 后在她背包 / 玩家背包里找（物品 id 是字符串，模组侧对注册表 + `isEdible` 双校验，接口层面依旧不收坐标）；
2. `maid.eat(level, stack, food)`——正常扣物品、放吃东西的音效与粒子、套食物效果，而且它内部就会发上面那个 `MaidAfterEatEvent`（所以「喂」与「检测喂」天然是同一套）；
3. 按营养值给好感度 / 回血，口径照 `DefaultMaidHealSelfMeal`。好感度**注册一个我们自己的 `Type`**（带冷却），避免反复投喂刷满——`Type` 就是个带冷却的数值来源，自己加一个是它留好的路子。

不碰她的任务系统，也不依赖日程，风险低。

### 要定的四件事

1. 躺下期间是否完全冻结她的移动（建议：冻结，且挨打自动起身）。
2. 躺下是固定时长还是躺到喊起来（建议：后者，另加「30 秒没动静就自己起身」的兜底）。
3. 投喂取谁的食物（建议：优先她自己的背包，其次玩家主手）。
4. 投喂算不算好感度来源（建议：算，但走我们自己的冷却）。

## 两侧的已知边界（汇总）

- **插件无状态、无定时器**：所有需要「记着上次」的设计都要么放模组，要么从台词表读回来。
- **回环端口无鉴权**：任何本地进程都能连上来让女仆说话、做这几个动作。动作参数全部过白名单，接口层面没有坐标入口，也不能执行指令。
- **单人游戏按 Esc 暂停**：模组的 tick 停摆，采样与动作请求的响应都会一起迟到（不是丢了）。反过来，动作的计时走游戏 tick，暂停期间不计入超时。
- **插件 handler 并发上限 4**：占满时那一帧会被静默丢弃（日志里有一行 warn）。事件风暴时可能丢帧。
- **进入 MC 的提示行按内容幂等**：改了提示的写法，下一次连接会补写一条新的（老那条留在历史里）；这样模型总能拿到当前版本的规矩。
- **连接刚建立的那一刻，别问「连上了吗」**（2026-10-16 真机上踩过）：宿主把 `connect` 交给插件时，它对这条连接的登记可能还没落定，`ws_status` 会说没连上。当时的写法把绑定前置了这个检查，于是绑定被静静跳过——现象是 MC 里说话与感知一起哑掉，只剩「她的话能上屏」这半边还通，看起来像模组没装。现在的做法：绑定直接问女仆是谁再发出去（不查连接状态），并且每次台词上屏时重申一次（幂等，模组只在目标真的变了时记一行日志）。
- **插件工具只在主聊天可用**：主动对话与剧本拿不到（见上「已知边界」）。所以五期的按需「看一眼」只在玩家跟她说话那一轮用得上。
- **她看不见的东西不该知道**：身边这一层只用她自己的位置、视线、光照与周围实体；站在背后但没遮挡的算她知道，被墙挡住的才算不知道。
- **身边那层首帧不出事件**：刚接上、换监控对象、女仆离开已加载区块再回来，都只重建基线；女仆回来时全局那层会重推一条 `state_snapshot`，那是「我丢线了」的信号。
- **协议里没有坐标**：只有档位（`close` / `near` / `far` / `gone`）、类别与一位小数的距离。
- **身边这一层的旁白也是记忆**：靠每类各自的冷静期压住频率（正常游玩是每小时几条到几十条），`［MC 事件］` 标记让它们可检索、可清理，永久记忆压缩是兜底。（2026-10-16 修订后只剩 `threat_near` 走这条路，其余改由开口时携带。）
- **模组还在推身边那五类事件，插件已经不理会**：修复只靠重启 LingChat 即生效，但模组每 5 秒仍在算、在发这几帧；`noticeEnabled` 关掉会连 `threat_near` 一起关掉（两者共用一个门）。要不要在模组那头摘掉，见「身边感知的改法修订」末尾那条待定。
- **`maid_look_around` 是本模组的扩展帧**：老 jar + 新插件时它会被回 `不支持的消息类型`，插件要如实转达；换回社区桥接模组时，五期之前的能力都在，只有这个工具不可用。`maid_set_task` 与 `maid_task_change` 同样是我们自己的扩展，老 jar 上换工作模式会回「不支持的消息类型」。
- **工作模式受她自己的日程与居家设置限制**：切成功只是换了任务，她按自己的作息干活；跟随状态有活时跟随行为让路，主人走远也不打断。插件不越权替玩家改这两项。攻击不受这条限制（模组自己驱动），但也追不出 32 格。
- **挖掘只挖够得着的方块**：不会为了追一块矿挖隧道（那是「挖矿工作模式」的事），也不挖水、岩浆与受保护的方块；方块要求正确工具而她没有时当场拒绝。掉落物进她的背包，装不下才掉地上。
- **有活且主人走远时，跟随行为会用 mixin 让路**：攻击、挖方块、走过去/躺床，以及非空闲工作模式，在主人超出原版回头线（半径 - 2）后不再把她拽回/传送回；主人靠近时照常跟随，活干完恢复。**不改活动半径**，拾物、找床、找餐桌、跟随距离保持车万女仆原版。被 Carry On 抱着时她不在世界里，气泡、动作与查询都用不了，放下后照常重推一次现状。
