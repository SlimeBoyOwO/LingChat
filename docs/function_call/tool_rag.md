## 背景

随着项目工具注册的规模越来越大，整体下来可能给 AI 注册的工具包括超过 30 个工具，尤其是还有插件外部扩展的情况下。为了保证 AI 的工具注册以及调用更好一点，现在提议建议使用 Tool Rag 机制来进行工具注册以及调用。

## 大致的思路

1. 实现 Tool Rag 的接口，把原来所有注册的工具灌输给上下文改成在 System Prompt 里面改成提示：“当你想为我做些什么，或者我要求你做什么的时候，你可以通过 tool_search 工具函数来查询是否有满足需求的工具，并尽可能调用已有工具，假如没有合适的工具可以承认自己做不到。
2. 确定 RAG 实现方案，尽量选择轻量化的方案。由于记忆检索系统以后可能也要用，选择合适的 RAG 方案。

## 注意事项

1. 竟可能不要对现有代码有较大的破坏
2. 可以设置个工具搜索缓存，避免每次都去查询工具。
3. 每次 RAG 搜索候选 5 个工具，并进入缓存。缓存中的工具采用类似 LRU 的机制，当缓存满了以后，把最久没有使用的工具移除。

## 实现

已按上述提案落地。与提案有出入的地方在下面逐条说明。

### 一个前置澄清

工具本来**不是**写在 System Prompt 里枚举的，而是通过原生 function-calling 的 `tools` 数组下发
（`tools/tool_loop.rs` 的 `stream_with_tool_loop` → `ToolRegistry::definitions_for_allowed`
→ `LlmClient::complete_stream_with_tools`）。所以本功能的实质是：**把下发的工具定义从
「权限全集」收窄为「常驻工具 + 检索激活的工具」**，并把「随附工具不够用就去检索」这层
要求写进人设系统提示词（`utils/prompt.rs` 的 `TOOL_USE_POLICY_PROMPT`），而不是每轮请求
临时插一条 system 消息——临时 system 会与人设层抢位置，模型也几乎不感知。

### 检索方案

ONNX 语义向量检索，模型 `bge-small-zh-v1.5`（512 维，uint8 量化约 23MB，单文件）。
代码在 `crates/ling-chat-notes/src/embedding/`（main 的 `ai_service::embedding` 是
re-export，调用路径不变），检索用到 `EmbeddingEngine::embed` / `embed_batch` 与
`cosine_similarity`，**将来记忆检索可直接复用挂在 `AppState` 上的同一个实例**（`state.embedding`）。

选它而不是词法检索，是因为语义检索对「换个环境」→ `scene_switch` 这类非同词命中更稳；
选它而不是更大的多语言模型，是因为工具只有 30~40 个、描述全中文，且模型文件会进每个
安装包（`prepare-desktop-resources.mjs` 整目录递归复制 `data/third_party/`）。

模型与分词文件不进 git（`.gitignore` 的 `data/**` 排除整个 `data` 目录），靠
`scripts/download_embedding_model.mjs` 获取；`pnpm run init` 已包含这一步。
换模型只需要改 `crates/ling-chat-notes/src/embedding/engine.rs` 的 `MODEL_DIR_NAME` 与下载脚本的 `BASE_URL` / `FILES`。

### 检索语料

每个工具可以挂一组「可能的提问方式」（示例问句）：

- 内置工具在 `definition()` 里用 `with_rag_examples([...])` 挂载；
- 插件工具在 manifest 的 `[[tools]]` 里写 `examples = [...]`。

检索时**示例问句优先**：每条问句单独算一个向量，查询与工具的相关度取所有问句里的最大
余弦。没有配置示例的工具回退到描述（只取描述，不拼英文工具名）。语料文本按「条数 +
每条长度 + 内容」做指纹，示例增删、改字、换序都会让该工具的向量缓存失效。

示例只参与本机索引：它们不在 `function.description` 里，不会随请求下发给模型，也不会
出现在 `tool_search` 的清单里。

### 常驻工具

**`tool_search` 与 `web_search`** 不走检索、每轮直接下发。`web_search` 仍受它自己的
开关与权限矩阵约束，不会被常驻强行放行。

### tool_search 的动态描述（关键）

只给模型一个「你可以检索」的入口、不给任何能力线索，模型不会想到去检索 —— 它会直接
回答做不到。所以 `tool_search` 的描述在**每轮下发前按当前可用工具重建**：把权限集里
除常驻工具以外的工具列成一份清单（工具名 + 一句用途，用途取描述第一句、过长时切在
逗号处），再附上「用一句话描述你想做的事调用本工具取证具体参数」的引导。

清单只到名字与用途，**参数不在其中** —— 具体用法依旧靠检索结果取得，token 收益不变。
真实注册表（35 个工具）下清单约 1.5K 字符量级，而完整 schema 要上万字符；跑应用时开
debug 日志可以看到实测的 `sent_chars` / `full_chars`（见 `tool_loop.rs` 的
「Tool RAG 工具集已收窄」）。

渲染逻辑在 `tool_rag.rs` 的 `search_description` / `apply_dynamic_search_description`，
由 `tool_loop.rs` 在算出本轮 `allowed` 后调用（`base_allowed` 决定清单内容，因此清单
天然不会泄漏该角色无权使用的工具）。

### 缓存

按**角色**为键，进程内跨回复保留，默认容量 5，可在设置页调到 1~20（推荐 10 个以下）；
超出时淘汰最久未被检索激活的。`tool_search` 与 `web_search` 是常驻工具、不占这个额度。
实现就是 `Vec<String>`（队首最重要），元素只有十来个，不值得引入 `lru` crate。
工具向量按「工具名 + 语料指纹」缓存（示例问句优先、描述回退），指纹变了才重算，
因此插件热重载/卸载不需要任何主动通知。

### 权限不变量

**权限永远优先。** `tool_search` 只在「该角色/场景本来就至少有一个可用工具」
（权限集非空）时才注入；检索语料只从权限集里取；激活缓存读取时始终与权限集求交。
因此收窄工具集不可能带来任何权限提升。该不变量有单测覆盖
（`tool_rag.rs` 的 `effective_set_stays_within_permissions`）。

收窄只决定**下发**，不决定**放行**：`ToolExecutor` 按「权限集 ∪ 本轮下发集」复核，
所以模型凭记忆直接调一个本轮没下发的工具照样执行——缓存只在进程内，重启就空，
而模型的记忆是持久的，拿「本轮没下发」当拒绝理由等于把缓存未命中变成对玩家的
「工具被系统拦下来了」（见 [permission.md](permission.md) §6）。这种情况下
`tool_loop` 会 `touch` 它，从下一轮起完整参数表重新下发。

反过来，放行也**不能只**看权限集：`tool_search` 按上面的不变量就在权限集之外，
只认权限集等于把检索入口自己锁死。

### 降级

模型缺失、`onnxruntime.dll` 不可用、分词或推理失败、当前 provider 不支持原生流式工具时，
一律回退到「全量工具下发」（即本功能之前的行为）并记日志。设置页有一个默认开启的开关
（`tool_settings.tool_rag`）可以手动关闭。

### 已知代价

工具首次使用会比原来多一次 LLM 往返（先检索、再调用），token 成本与延迟都上升。
按角色的激活缓存让同一角色已检索过的工具在后续回复里持续可见，是主要的缓解手段。

缓存**不跨进程**：重启之后模型凭记忆调工具（台词表里还留着上次的检索结果）会被
重新激活并照常执行，但那一轮它看不到参数表，只能靠记忆里的旧 schema 猜。
真要避免，得在重启后的第一轮先检索一次——目前不做这件事。

```bash
# 拉模型
node scripts/download_embedding_model.mjs

# 纯逻辑单测（不需要模型）：LRU、权限求交、语料回退与指纹、最大余弦、序列化隔离

# 真实模型下的嵌入冒烟：维度、归一化与语义区分度。

cargo test -p ling-chat-main --lib threshold_smoke -- --ignored --nocapture
```

## 工具推荐（每轮发言前点几件）

RAG 收窄工具集之后，另一个问题浮出来：**模型想不起来去 `tool_search`**。它不会主动检索
自己不知道存在的东西，`tool_search` 的动态描述只是把清单摆在那里，能不能想到用全看运气。

于是加了一步可选的预处理：每轮用户发言时先算出「这一轮可能用得上」的工具，作为一条
**临时记忆**（`{旁白: （系统提示：参考推荐工具：a、b）}` 信封，由 `status_ops::RequestScoped`
注入本轮请求），并把它们并进本轮的 `effective_allowed`。设置里三选一
（`tool_settings.tool_recommend_mode`，默认 `off`）：

| 模式    | 谁来挑                                                                    | 额外成本               |
| ------- | ------------------------------------------------------------------------- | ---------------------- |
| `off`   | 不推荐                                                                    | 无                     |
| `agent` | 上帝 Agent 读最近 `recent_window` 条台词，用 `recommend_tools` 决策工具挑 | 每轮一次小模型调用     |
| `rag`   | 拿玩家这句话静默检索一次工具（与 `tool_search` 共用嵌入模型和激活缓存）   | 本地向量计算，不调模型 |

两条路径的共同约定：

- 提示是**临时**的：只搭本轮第一个请求，不写台词表、不进长期记忆，下一轮重新算
- 挑中的名字先过一遍权限集再并进本轮工具集——**推荐不构成授权**
- 没有推荐（或都不过阈值）时什么都不加
- 推荐失败只记 warn，不能拖累这一轮回复；Tool RAG 关闭时全量下发，推荐在工具集上是空操作，
  提示仍然有效

候选范围就是当前角色在当前来源下的**权限集**：设置页里没开的工具组（文件、媒体、技能等）
不会参与检索，也就永远不会被推荐。天气与背景特效原本不属于任何工具组，装了也用不上；
现在 `query_weather` 归入「状态查询」、`set_background_effect` 归入「场景切换」，
开启对应分组即可。

### `rag` 模式的阈值

静默检索每句话都会跑，所以必须有一道分数闸门，否则「晚上好呀」也会被推荐几个不相干的工具。
阈值 `AUTO_RECOMMEND_MIN_SCORE = 0.65`，最多推荐 `AUTO_RECOMMEND_TOP_K = 3` 件。实测依据在
校准用例 `threshold_smoke`（需真模型，用 `--ignored` 单独跑，详见下方验证命令）：

- 明确的工具意图 top-1 落在 0.65~0.86（「帮我加个日程」0.654、「今天天气怎么样」0.691、
  「换个场景吧」0.708、「现在几点了」0.858）
- 寒暄与闲聊 top-1 都在 0.64 以下（「晚上好呀」0.594、「我今天心情不太好」0.633）
- 早先两个漏检（「看看我建的爱心」「你还记得我上次说过什么吗」）配上示例问句后分别达到
  0.795 / 0.824，已经能正常推荐

改示例问句或回退描述都会改变分数，`threshold_smoke` 会因此失败——重跑一遍、重新校准即可。

语料结论：**示例问句优先，没有配置时只回退到中文描述，不拼英文工具名**。旧语料时期实测
英文名字对中文短句只是噪声（`schedule_add_todo` 这类 token 会把相关分数整体压下去），
回退路径沿用这个结论。

命中项照常进入该角色的激活缓存，与 `tool_search` 共用 LRU（默认容量 5，可调 1~20），推荐过的工具在后续
几轮一直可见，直到被淘汰。`tool_search` 自己的检索不设阈值（模型主动要的东西总得给），
传的是负无穷。

## 回复后推荐（AI 说完也补一次）

前置推荐只看玩家这句话。模型有时会先说自己要做什么（比如「我去看看你的屏幕」），却因为
对应工具不在本轮下发集合里而没有调用；玩家下一句未必还会提这件事，前置推荐就补不回来。

生成结束后的收尾工序会拿本轮落地的助手台词（正文 + 动作）再静默检索一次：命中的工具进
该角色的激活缓存，同时暂存给下一轮请求。阈值、候选池与前置推荐完全共用，同样只是一条
临时提示，不写台词表、不进记忆。

两条推荐不会同时出现：下一轮请求优先用当轮前置推荐的结果；只有当轮没算出结果时才呈现
上一轮暂存的那份，暂存只保留最后一份。Tool RAG 关闭、推荐模式为 `off`、剧本来源或编辑器
试玩时这一步直接跳过；本轮已经调用过工具的回合也跳过，避免下一轮把同一件事再做一次。

### 调试指令

在聊天框输入，只在后端日志输出：

- `/查看注册工具`：注册表里的全部工具（内置 + 已启用插件）
- `/查看所有工具`：当前角色在自由聊天场景下权限允许的全部工具
- `/查看推荐工具`：当前角色的激活缓存、下一轮暂存的回复后推荐，以及最近一次静默检索
  在过阈值前的前三名分数（用来解释「为什么这句没推荐」）
