# ASR 热词系统 · 设计

本文档描述该系统的设计、架构、关键决策**与已实现的功能**，供评审与后续维护查阅。

## 1. 概述

热词在两个层面服务识别准确率：

- **角色层面**——每个角色一套热词，切角色即换词表。角色名自动注入，无需手工维护
- **全局层面**——跨角色通用的词（用户自己的口头禅、常说的专有名词），所有场景追加

热词**不进 provider 配置**。它是**调用级参数**：识别时由调用方现取现传，随角色切换而变。
配置级热词会让用户「填了不生效」，这条边界在早期就被明确划出并保留至今。

## 2. 架构

### 2.1 三层数据模型

```
【生产层】素材，不参与识别
    library_hotword（分类词库）
         │
         │ 拷贝式添加（非引用）
         ▼
【存储层】识别的唯一真相
    role_hotword    （逐角色）
    global_hotword  （全局追加）
    角色名           （不进库，每次现取）
         │
         │ 合并去重，按优先级排序
         ▼
【发送层】快照 + 派生，不持久化
    有序词表 ──▶ 识别请求
```

**关键分离**：

- **词库不参与识别**——它只是「素材库」，角色热词/全局热词才是识别的唯一真相。从库到角色是
  **拷贝**，不是引用
- **角色名不落库**——每次识别时从当前场景现取，见 [3.4](#34-角色名在场即注入)
- **发送层是派生的**——有序词表由上述三个来源合并而成，不持久化

### 2.2 发送链路

```
角色/在场角色变化
    └─▶ 刷新场景热词缓存（异步读库，带版本号）

录音开始
    └─▶ 取快照（冻结本次识别的词表）

识别（两条路都取同一份快照）
    ├─ 流式：会话建立时下发，边录边发
    └─ 非流式：录完整段后随音频一起发
              │
              ▼
       归并去重（按 text 取最大权重）
              ▼
       provider 侧按容量截断
              ▼
           识别服务
```

**快照与冻结**：词表在**录音开始时**取一次，一次识别全程不变。中途切角色不会让本次识别换用新词表
——流式会话尤其如此，词表在会话建立时就已下发给服务端，撤不回来。

**过期保护**：缓存刷新是异步的，而读取是同步的。切角色后、读库尚未返回时用户就按下录音键，
会读到**上一个角色**的词表。因此缓存带一个递增的版本号，读取时校验；不匹配则本次**弃用整份词表、
不带任何热词**——宁可不加偏置，也不用错角色的词表。这是刻意的：用错角色的词比没有词更糟。

## 3. 设计决策

### 3.1 热词的归属：角色级 + 全局级

| 决策     | 取值                                               |
| -------- | -------------------------------------------------- |
| 角色热词 | 每个角色独立一套，存数据库。切角色即换词表         |
| 全局热词 | 独立作用域，与角色热词取**并集**（同词取最大权重） |

**为什么不放角色的 `settings.yml`**：角色目录是「可分享、且会被外部覆盖」的——插件角色目录是
运行时直读的，插件更新可能直接覆盖它；用户手工删除角色目录或换机器时热词也会跟着丢。热词是
用户私有数据，不该住在一个可能被第三方覆盖、或随角色包一起分发的文件里。

**参与集合**：主角 ∪ 在场角色，**排除**玩家本体与「尚未选定主角」的哨兵值。只发主角的话，
多角色场景里用户喊配角名字就识别不出来。

**玩家自己的名字不纳入**：无明确需求；场景里需要识别的人名由各角色的热词覆盖。

### 3.2 顺序即优先级

热词列表是**有序**的，顺序由确定性规则给出：

```
角色名（主角 → 在场角色）  →  角色热词（主角 → 在场顺序 → 插入顺序）  →  全局热词
```

**全局词排在最后**：它是最通用的层，任何具体角色的词都比它更该保住。（词集功能实现后，
词集词会追加在更靠后的位置——见 [5. 未实现的设计](#5-未实现的设计)。）

**顺序不是风格问题，是功能**：超出容量时从**尾部**丢弃，所以顺序决定了哪些词一定保得住。
主角排在最前，意味着截断时主角的词最后被丢——这是结构性保证，不依赖任何运行时判断。

**因此不需要「排序」列**：以上规则已经给出全序，用户无需手工排序。

### 3.3 合并与去重

**存储层不合并**：角色 A 和角色 B 都用「张三」这个词，库里存**两行**，各自的权重、增删互不影响。

理由是**权重是「这个角色有多希望这个词被识别出来」的意图表达**——A 想给高权重、B 只想要默认值
是合理差异，不该被强制统一。共享存储还会带来引用计数与孤儿清理的复杂度。

**发送层必须合并**：同 `text` 取**最大权重**，保留首次出现的位置。

取 max 而非「先到先得」——两个角色都要这个词，最强的意图该胜出。先到先得会让结果取决于角色
顺序，用户无法理解为什么改了权重没效果。

### 3.4 角色名：在场即注入

| 项   | 取值                                                  |
| ---- | ----------------------------------------------------- |
| 来源 | **每次识别时现取**（主角名 + 在场角色名），不进数据库 |
| 权重 | 5（普通档的「强制偏好」档）                           |
| 位置 | 排在热词列表**最前**                                  |
| 去重 | 与用户热词同 `text` 时取最大权重                      |

**为什么现取而不是物化成一条热词**：物化 = 快照。角色改名后那条热词不会跟着变，需要用户手动
改。现取从根上消除这个问题——名字一改，下次识别自动生效。

**派生的时机**：它在刷新场景热词缓存时**同步**派生（不经过数据库往返），因此切角色、改名都能
立刻反映到下一次录音的快照里，也不受读库成功与否的影响。

**已知取舍**：用户**无法删除「角色名」这条热词**。这是有意的——角色名是最该被识别出来的固有名，
且按优先级规则它排最前、截断时最后被丢。若将来用户反馈不想要，正确做法是加一个**开关**，
而不是回到物化。

> **替代了**：早期设计中的「默认热词 = 角色名，物化成真实词条」及其配套的「角色改名不跟随」
> 决策。见 [6. 已废弃的决策](#6-已废弃的决策)。

### 3.5 分类词库：拷贝式素材库

词库是一套**按情景分类**的词条集合，作为所有热词的素材来源。

| 决策      | 取值                                                 |
| --------- | ---------------------------------------------------- |
| 关系语义  | **拷贝式**——「添加到角色」= 复制一份，落地后各自独立 |
| 库内改/删 | **不回传**到已拷贝的词条                             |
| 容量      | 词条 ≤ 2000、分类 ≤ 100、分类名 ≤ 30 字符            |

**为什么拷贝而非引用**：引用式共享会导致改一个词影响所有角色，还要维护引用计数与孤儿清理。
而库的唯一价值是「免去重复录入」，不是「统一维护」——后者与「权重是角色级意图」直接冲突。

**为什么在角色侧做选择器而不是库侧指派**：角色热词的编辑模型是「弹窗内编辑 + 底部保存 +
取消即丢」。库侧直接写角色热词会绕过这个模型，同一份数据出现两种提交语义。角色侧选择器完全
落在既有草稿模型里——**后端零新增写入路径**。

**已知取舍**：库中改了错字不会更新已拷贝的词条。接受它；将来若需要，升级路径是给词条加来源
标记 + 显式的「与词库对齐」动作，**不做静默传播**。

### 3.6 取值口径：权重与文本长度

两个口径都来自服务商的第一手文档，**不是自造值**。

**权重不是连续区间**：

> 权重取值范围为 **[1, 5] 或 50**：取 [1, 5] 为普通热词，值越大偏好越强；取 50 为超级热词，
> 召回率大幅提升，但**超级热词最多不超过 50 个**。

- `6..=49` **无效**，归一时就近取合法值
- 超级热词（权重 50）一次请求最多 50 个，超出部分**降级为普通档**而非丢弃——权重只表达
  「偏好强度」，降一档不会让词消失，而丢弃会连带影响它后面排队的词
- 配额是**发送层**的兜底，不是保存时的校验：各作用域各自合规也拦不住并集超限（三个角色各 50 个
  就是 150），且用户不该因为「另一个角色也设了超级热词」而保存失败

**文本长度是两套判据**（[3.11](#311-文本长度判据的分支) 讲为什么必须分成两支）：

| 词条形态        | 判据                         |
| --------------- | ---------------------------- |
| 含非 ASCII 字符 | 总字符数 ≤ **15**            |
| 纯 ASCII        | 按空格切分后的片段数 ≤ **7** |

**不能压成一个数**：`DeepSeek-harness`（16 字符）走纯 ASCII 分支合规，而任何含中文且超过 15 字
的词都不合规。

**存储侧还有条数上限**——每个作用域**各 200 条**（角色热词、全局热词分别计），保存时校验、
先校验后写。这是**存储**的上限，与下面 provider 的**发送**容量是两件事：单角色存 200 条，
但云端的即时热词上限是 2000 条——反过来说，**单角色永远存不到 2000 条**。

### 3.7 容量与截断

**截断位置**：不在发送层的归并里，而在**各个构造请求载荷的地方**——共三处：本地 provider 的
转写请求、云端 provider 的同步请求、以及流式会话的参数构造（流式路径不经过 provider 实例，
所以它是独立的一处）。

理由是**截断判定必须与真正发出的字节由同一段代码产生**。早期方案把截断放在命令层，而请求格式
在 provider 层，两者靠跨模块手工对齐常数——必然漂移。差值虽只有几个字符（前缀后缀），后果却是
**日志报「无溢出」而实际静默丢词**，正是这套设计要消灭的失效模式。

**各 provider 的容量**：

| provider                    | 热词如何生效            | 容量                                                 |
| --------------------------- | ----------------------- | ---------------------------------------------------- |
| 本地 llama-asr              | 转写请求的 prompt 偏置  | prompt 字符预算（**权重不生效**，prompt 无权重语义） |
| 云端 qwen（支持即时热词）   | `parameters.vocabulary` | **2000 条**                                          |
| 云端 qwen（不支持即时热词） | 不发，记日志丢弃        | —                                                    |

⚠️ **本地 provider 那个字符预算没有文档依据**，是代码里的自造值；真机真正的限制是部署参数里的
上下文窗口（prompt 与音频共享），余量远大于此。这是已知的待办项（它与该 provider 的另一处回归
修复应一起做），**不属本次改动范围**，但不应被误读成厂商给出的规格。

**为什么 qwen 侧必须本地截断**：服务商文档明确写着超限时**静默随机丢弃**——

> 合并后超过 2,000 个时，**随机选择 2,000 个使用**。

随机丢弃会摧毁优先级保证（主角名可能被随机丢掉），且用户无法察觉。本地截断后永不触达服务端
的随机分支。

**溢出不是故障，是配置问题**：被丢弃的一定是列表尾部最低优先级的词，识别照常进行。
因此**不做 UI 报警**，只在**程序日志**里留痕（used / dropped / capacity）。

⚠️ **但要注意日志级别**：本地 provider 的记账是 **debug 级**，默认日志过滤器下**看不到**；
云端侧是 warn 级。排查截断问题时需显式调高日志级别，否则会误以为「没有溢出」。

设置页只做**能力展示**（「这个模型最多收多少」），且仅对**真正会下发热词**的模型显示——给一个
根本不发词的模型显示「能装 2000 条」会与「配了不生效」的警告直接打架。

**不做频率淘汰**：热词是用来修正**模型不认识**的词，生僻词天然低频——纯频率驱动会优先淘汰掉
最需要的防护。且缓存退出即清零，计数每次重启归零，等于每次重新学。

### 3.8 LAN 同步：镜像语义

| 决策         | 取值                                                                              |
| ------------ | --------------------------------------------------------------------------------- |
| 是否纳入     | **纳入**，随 `role` 表一起镜像（角色表所在的整批表）                              |
| 参与镜像的表 | **四张**：`role_hotword`、`global_hotword`、`hotword_category`、`library_hotword` |
| 语义         | **镜像**——同步后本地的这几张表就是对端的拷贝                                      |
| 失败处理     | 整批回滚：要么全部换成源端数据，要么全部不动                                      |

**为什么必须纳入**：热词绑角色 id，而角色表本身被镜像。不纳入的话，同步后热词仍按旧 id 指向，
轻则留下孤儿行，重则**角色 id 已被另一个角色占用 → 热词挂到错误的角色上**（静默错配，用户无法
察觉）。另有两条旁证：记忆库是同形数据且早在同步之列；「不纳入 + 同步时清掉」的方案等于每次
同步静默删光用户的全部热词。

**行为代价**：热词是镜像语义——同步后本地对热词的修改会被对端覆盖。与记忆、存档一致。

⚠️ **已知风险（本系统最严重的一条）**：旧设备发来的数据包缺热词字段时，会被解析成空数组，
退化为「本次同步清空热词」。这是不给传输结构引入协议版本号的直接代价，**当前接受**。

**但要注意损失量级**：清空角色热词是「重录十几条」，而**清空词库是用户整理多时的整套分类素材
归零**，且词库没有兜回机制。这是本系统里**唯一一条「不报错但静默清空用户输入」的路径**——
保留式导入本可消除它，代价是让这两张表与其余已入镜像的表语义分叉，当前决策是不分叉。
**若将来有用户反馈丢库，第一个该改的就是这里。**

### 3.9 归档：热词不随角色包移动

**热词不是角色的属性，是「人用什么词」的属性。**

同一个人用不同角色，常用词高度重合（自己的口头禅、常说的专有名词、自己的名字）；而同一个角色包
到了别人手里，原主人的热词对他毫无意义。把热词打进角色包，等于把 A 的使用习惯带给 B。

**已知的静默不一致（接受）**：覆盖导入时角色 id 不变，因此热词仍指向有效行——**换了角色包但热词
还是旧的**。触发条件很窄（该角色原本有热词，且用户用覆盖策略导入另一个同名角色包），且语义上
也不算错——按「热词是人的属性」这条理由，保留原词表反而是自洽的。

**不影响 LAN 同步**：LAN 是**设备间镜像**，两端是**同一个人**，热词必须跟着走。归档是「角色包」
（可能给别人），LAN 是「我的另一台设备」——两条链路的语义不同。

### 3.10 数据模型细节：无外键

四张热词表（`role_hotword`、`global_hotword`、`hotword_category`、`library_hotword`）
**都刻意不写 `FOREIGN KEY`**。不是遗漏，是取舍。

**原因：外键会挡住旧版客户端。** 仓库里 `role` 表的删除走的是 `DELETE FROM role`，
旧版二进制不认识这两张新表，一旦外键存在（且开 `PRAGMA foreign_keys`），这条 DELETE
会被约束拒绝——**用户升级到新版之前，连删角色都做不了**。

**代价：级联删除要自己兜。** 没有数据库层保障，删角色时的热词清理落在应用层（见
[4. 已实现的功能](#4-已实现的功能) 里的级联清理条目）——这也意味着绕过应用层直接改库会留孤儿行。

**写入入口同一口径**：既然没有数据库约束兜底，各写入路径（角色 / 全局 / 词库 / LAN 导入）
必须自建同一套校验与归一（权重离散口径、文本长度判据、条数上限），不能有一个入口放宽。
LAN 导入尤其要拦——对端 payload 里的脏值必须在落库前归一，否则镜像会把它扩散到本机。

### 3.11 文本长度判据的分支

| 词条形态        | 判据                         | 例                                             |
| --------------- | ---------------------------- | ---------------------------------------------- |
| 含非 ASCII 字符 | 总字符数 ≤ **15**            | `厄洛替尼盐酸盐`（7 字符）通过                 |
| 纯 ASCII        | 按空格切分后的片段数 ≤ **7** | `The effect of temperature variations…` 不通过 |

**为什么不能压成一个数**：两条判据的数量级完全不同。`DeepSeek-harness`（16 个字符）
走纯 ASCII 分支是合规的，而任何含中文且超过 15 字的词都不合规。若统一按字符数卡，
要么放过一整个中文长句，要么把正常的英文术语误杀。**分支由「含不含非 ASCII」决定，
不是由长度决定**——后者会循环依赖。

**归一发生在写入前、校验失败即在 UI 就地标记**（不是保存后才报「保存失败」）：超长的行
在用户还在编辑时就被标红并给出具体数字（`{count}` / `{max}`），保存按钮据此拒绝。
判据在后端是**单一真相**，前端只做同口径的展示层拦截。

### 6.1 组内顺序

**在已废弃的 §6 之下保留这一小节，是因为编号被代码引用**（`hotword_repo.rs`
与 `api/hotword.rs` 的文件头注释）。编号保留原样、不改指他处，正是为了让那些注释
**在本次改动后仍能原地解析**——这比编号美观重要。

内容本身**仍然有效**（它是 [3.2 顺序即优先级](#32-顺序即优先级) 的实现口径）：

- **存储层无「排序」列**：每条热词只有一个自增 `id`，列表顺序 = `id` 升序 = **插入顺序**。
  没有可写的 `sort_order`，用户无需（也不能）手工排序
- **发送层按确定性规则拼装**：主角 → 在场顺序 → 组内插入顺序，三段拼接后即为全序
- **不重排、不去重（在归并之前）**：场景级查询返回的是「主角的词 + 各在场角色的词」的
  顺序拼接，跨角色同名在此**各返回一条**、不合并——合并是发送层按 `text` 取最大权重时
  才发生的（见 [3.3](#33-合并与去重)）

**为什么顺序不能由存储层决定**：优先级规则里有「在场顺序」这个运行时概念，它在写库时
并不存在。顺序只能由发送层现算。

## 7. 事务与自锁

**热词的每一次保存都是单事务整表替换**，不是逐条增删。角色热词、全局热词、词库
三处同款。校验失败时**整表保持原样**——不会出现「删了一半、加了一半」的中间态。

**⚠️ 事务里必须传 `&txn`，不能传 `&db`。** 这是本仓库最容易踩的一个坑：

SQLite 连接池在本项目的配置下是**单连接**。在事务内部把连接池（`&db`）再传下去，
等于向已经在事务里的同一个连接再要一次——**自锁**，表现为请求永远挂住而不是报错。

因此仓储层的写函数签名收的是泛型连接（既接受 `&db` 也接受 `&txn`），**由调用方决定**
开不开事务；仓储自己不隐式开事务。凡是「在事务里」的调用点（`api/hotword.rs`、
`api/role_archive/import_pipeline.rs`）都必须显式传 `&txn`。

**为什么不做成仓储内部自动开事务**：`replace_for_role` 这类整表替换需要与**调用方的
其它写入**（例如归档导入的多个步骤）在同一个事务里，事务边界属于调用方。仓储代开事务
会把边界焊死，归档导入就只能分多次提交，失败时回滚不完整。

**提交语义与草稿模型**：角色热词在弹窗里是**草稿**——用户改动先落在前端草稿，
点底部「保存」才一次提交。词库侧同样落在既有草稿模型里，**后端零新增写入路径**。

## 8. 运行时链路

### 8.1 场景热词缓存与录音快照

缓存的写入是**异步**的（一次数据库往返），读取是**同步**的。这个不对称是整个运行时链路
最容易出错的地方，因此缓存带一个**递增的版本号**：

- 每次刷新**开始时**版本号 +1，旧缓存同时作废
- 读取时校验版本号；不匹配说明中间发生过刷新，本次**弃用整份词表**（不带任何热词）

**宁可少带热词，也不带错角色的词表。** 切角色后、读库尚未返回时用户就按下录音键，
若不校验就会拿上一个角色的词表去识别——整段话都偏置到错误的词上。空表只是没有增益，
错表是主动引入错误。

**失败路径同样要复位版本号**：一次刷新失败若不复位，会让「本次失败」退化成
「整段会话都没有热词」——快照的校验永远通过、内容永远为空。这是实现期踩到的坑，
复位写在 `catch` 里。

**触发时机**：主角变化或在场角色变化即重取。角色名热词不经过这条链路（它是同步派生的，
见 [3.4](#34-角色名在场即注入)），因此不受读库失败影响。

词表在**录音开始时取一次快照**，一次识别全程不变。有意的：

- **流式会话尤其如此**：词表在会话建立时就已下发给服务端，撤不回来
- 中途切角色**不会**让本次识别换用新词表——否则会出现「前半句用 A 的词、后半句用 B 的词」
- 快照与「录音开始时的输入框内容」同类：都是本次录音的**输入参数**，与录音期间的界面
  状态无关

**两条识别路径取同一份快照**：流式（边录边发）与非流式（录完整段再发）在
**录音开始的那一刻**取快照，之后不再读缓存。差别只在**下发时机**——流式在会话建立时
下发，非流式随音频一起发。这样两条路径的词表语义完全一致，不会出现「切了个开关，
热词行为就变了」。

### 8.2 模型不使用热词时的提示

某个模型**完全不使用热词**时，设置页显示一条显式提示。判据是两条**并列**的生效链路：

| 能力位                       | 含义                                         | 谁走这条               |
| ---------------------------- | -------------------------------------------- | ---------------------- |
| `supports_inline_vocabulary` | 支持即时热词 `parameters.vocabulary`         | 云端 qwen-audio-3.x 系 |
| `supports_prompt_bias`       | 热词经 `prompt` 上下文偏置生效（权重被忽略） | 本地 llama-asr         |

**两者都为 false 才提示**——不合并成单个「支持热词」位，因为它们是 provider 侧两套
不同的协议能力，各自的门控也仍分开判定。**本地 llama-asr 正是走 prompt 偏置的那条**，
若只看即时热词位，它会被误报成「配了不生效」。

**提示与容量展示是两件事**：提示说的是「会不会生效」，容量说的是「能装多少」。
容量的 `null` 有**两种**含义（不支持 / 无条数上限），因此**不能**把 `null` 一律读成
「不支持」——判据是上面那两个能力位，容量只用于展示（见
[3.7 容量与截断](#37-容量与截断)）。
