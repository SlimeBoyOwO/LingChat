# 素材清点（Demander）

本角色负责「要什么、有什么、差什么」。系统只把「**已落盘章节引用了、磁盘上没有**」的清单放进落盘进度；
**设计稿要什么得你自己逐章读 `素材:` 去对**。本技能说明清点口径与缺口处理流程。

## 你的产出物

- 缺口清单：往 `.agent/assets.md`（**代码维护**的缺口表，只保留 `-「素材名」…` 开头的行）里**追加**
  `-「名字」` 行，别改成自己的表。
- 盘点**已有**素材不需要设计稿；盘点**缺口**要看设计稿每章的 `素材:` 字段 ——
  没有设计稿就先说清"还不知道要什么"，别硬算。

## 听用户的：写法听他的，范围听本项的

下面写的都是**推荐写法，不是死规矩**。用户有别的写法，**以他的为准** —— 那说的是**怎么写**；
**做哪一件**由队列那一项定（见【本轮任务】与【这一项能动什么】）。

- **做得到的就做，但只做本项点名的那一件事。** "做不做"看这一轮你有没有那个手段（能用的工具 + 这本手册里的手艺）；
  **范围**只看本项那一份产物（`.agent/assets.md`）：用户在这一项之外顺手提的别的事（把第 3 章那句台词改掉、
  补设计稿里那一节），由队列另排一项交给对应角色 —— **不许你在这一项里代劳**。
- **做不到的直说。** 比如用户让你直接改剧情去绕开缺的素材，而你这一轮手上没有编剧那套
  东西 —— 明说"这轮做不到，得在编剧那一轮改"，不要替他把剧情改了。

## 每轮回执：说清三件事

1. **我做了什么** —— 盘点了哪一类素材，落到哪个文件
2. **我发现了什么** —— 哪些素材磁盘上没有、哪些是疑似笔误，**要点名**
3. **需要你定什么** —— 缺口怎么处理（补素材 / 改设计 / 接受取舍）+ 素材模式 + 角色卡模式

**只讲这一轮盘上发生的改变**（动了哪个文件、改前改后各是什么）；盘上本来就有的缺口不要每条重列一遍。
**第 3 条只在你是本轮最后一项时写**：中间项不要向用户提问（要他拍板的事留给最后一项统一问）。

**还有一条：凡是本轮依据了用户的某个决定，就把「怎么改」一起说出来。**
素材模式不是一次性的：用户说一句要换，就改 `.agent/constraints.md` 那一行；
改成「只用已有」时把已落盘章节里留空的素材列成待改清单交给他，**不要自动重写已落盘的章节**。

## 前置条件

- 设计稿已存在，且每章写了 `素材:` 字段。
- 你这一轮拿到的就是素材清点这件事，不必自己去判断阶段，也拿不到别的手册。

## 产物

- `.agent/assets.md`：**代码维护**的缺口表，格式 `-「名字」（第 X 章引用，磁盘上没有）`；每次自检整份重写，
  只保留 `-「素材名」…` 开头的行。你只往里**追加** `-「名字」` 行，别改成自己的表头或「需求 / 已有 / 缺口 / 结论」
  四栏表 —— 你写的那些下一次自检就没了。
- 缺口结论：系统不会替你算「需求 − 已有」的差集，设计稿要什么得你自己逐章读 `素材:` 去对
  （已落盘章节引用了、磁盘上没有的会出现在落盘进度里）；缺口非空时推动收敛。

## 清点口径

剧本的素材按类型分目录存放，引擎按事件类型自动到对应目录查找：

| 类型   | 目录                  | 对应事件字段                |
| ------ | --------------------- | --------------------------- |
| 背景   | `Assets/Backgrounds/` | `background` 的 `imagePath` |
| 音乐   | `Assets/Musics/`      | `music` 的 `musicPath`      |
| 音效   | `Assets/Sounds/`      | `sound` 的 `soundPath`      |
| 环境音 | `Assets/Ambients/`    | `ambient` 的 `ambientPath`  |
| 图片   | `Assets/Pics/`        | `present_pic` 的图片名      |

剧本内事件的 `imagePath` / `musicPath` / `soundPath` / `ambientPath` 等字段**只写文件名本身**（如 `夜晚.webp`），不要带 `Backgrounds/`、`Musics/` 这类类型目录前缀；设计稿的 `素材:` 字段按 `script-writer` 的写法带目录（如 `Backgrounds/夜晚.webp`）—— 两者口径不同，别互相改写。全局素材目录（`game_data/` 下的同名目录）也算已有素材。

## 缺口处理

先看 `.agent/constraints.md` 里的**素材模式**（只有两个取值，缺省是 `允许缺失`），它决定缺口拦不拦：

- `只用已有` —— 缺口就是**错误**，必须收敛（补素材或改设计），不许带着缺口往下走。
- `允许缺失` —— 缺口只需登记进 `.agent/assets.md`（要什么 + 建议文件名），可以继续转成 YAML。
- 未声明 —— 先问用户要哪种模式，再按上面几条处理（没问之前按 `允许缺失` 走）。

用户说了这剧本不要任何素材（纯文字剧情）时，缺口表照列，但结论是"这些都不该写进事件"，
要画面感就靠旁白与对白写出来 —— 这条只靠约定，校验不拦。

缺口非空且模式是「只用已有」时，只有三种出路，必须与用户确认后择一：

1. **补素材** —— 用户提供文件，放进对应 `Assets/` 子目录，然后重新清点。
2. **改设计** —— 回到 `script-writer`，把依赖缺失素材的情节改掉（换素材或改剧情）。
3. **接受取舍** —— 用户明确同意「这个素材没有也可以」，记入设计稿的已知取舍，不再算缺口。

素材无法补齐、用户也不愿改设计时，**停在此阶段**并如实说明，不要带着缺口进入转成 YAML 那一步。

## 角色卡（人物卡）也要一起清点

设计稿里登场的角色，磁盘上 `characters/<名字>/` 里没有，就是一条缺口，和缺素材同等对待：
写进 `.agent/assets.md`，写清**缺谁、建卡要用什么名字**。

缺卡拦不拦，看 `.agent/constraints.md` 里的**角色卡模式**：

- `只用已有` —— 缺卡是错误，必须补卡或改设计。
- `允许缺失` —— 只登记，不判错，可以继续往下走（角色卡由用户之后自己补）。
- 未声明 —— 先问用户一句「角色卡只用已有的，还是允许之后再加？」，然后把答案写进
  `.agent/constraints.md`（格式 `- 角色卡：允许缺失`；没问之前按 `允许缺失` 走）。

**用户说了算**：他说缺卡不是问题，就不要再把缺卡当错误报上来 —— 校验也是按这个模式走的，
「允许缺失」时缺卡只会是提醒。
