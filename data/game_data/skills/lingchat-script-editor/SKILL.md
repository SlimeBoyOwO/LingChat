# LingChat 剧本编辑器 · 流程总纲

**本文件是流程判断的依据，不是落盘规范。** 它回答一个问题：用户这一句，这一轮该做什么。
真正动手的角色各自读自己那本手册（编剧 / 素材官 / 落盘 / 校验），这里不重复它们的手艺。

## 一条对话的走向

- **创建新剧本**：剧本类型 → 大纲与工程创建 → 内容设计 → 逐章撰写 → 完成与交付
- **修改已有剧本**：读现有内容 → 按用户需求逐项改 → 完成与交付

**一轮里做多少，看队列。** 用户这一句里明确要的事全部排进 `tasks`，
**队列全部做完才算这一轮结束** —— 只做了一半就收尾是错的。
用户只说「继续」这种没指明的事，默认就是一章。

## 怎么判"用户这一句要做什么"

| 用户说的话                                                         | 任务                         |
| ------------------------------------------------------------------ | ---------------------------- |
| 跟这个剧本无关：闲聊、问软件怎么用、道谢                           | `chat`                       |
| 讲自己的想法 / 喜好 / 设想，**还没让写**（「我想让主角是个剑客」） | `summarize`                  |
| 缺关键信息得先问（这一章讲什么、一共多少章、主角是谁、素材怎么来） | `collect`                    |
| 要求写剧本 / 改剧本（「写大纲」也是这个）                          | `outline` / `revise_outline` |
| 明确要求写某一章（「你把第 9 章写出来」）                          | `write_chapter`              |
| 要求改已经写好的章节内容                                           | `revise_chapter`             |
| 盘点素材：要什么 / 有什么 / 差什么                                 | `check_assets`               |
| 校验、修错、收尾                                                   | `polish`                     |

**「给想法」和「下指令」的分界**：只是描述想法、喜好、设想 —— 一律 `summarize`，
产出物是复述 + 问缺口，不是正文。

**「写」和「落盘」是两件事**，在任务类型之外单独判（`land` 字段）：

- **写**（写剧本 / 写大纲 / 写章节 / 把剧情写出来）= 把内容写出来给用户看，**不写文件**。
- **落盘** = 变成文件。只有用户明说了落盘（落盘 / 生成章节 / 写进 Chapters / 存下来），
  或者他是在回答你上一轮问的「要不要落盘」并答了要 —— 才是落盘。
- 认不出就 `land: false`：多问一句的代价，比凭空生成一堆文件小得多。

**认不出就用 `chat`。** 这一条没有例外：`chat` 只回话、不动任何文件，猜错的代价最小。
跟剧本有关还是无关，看它谈不谈这个剧本的人物、情节、章节、素材。

**会话没绑定剧本时**（编辑器里没打开剧本就新建的会话）：这只说明"用户还没说是哪个剧本"，
不是"你可以自己挑一个"。候选列给用户让他选，或者问他要新建的剧本叫什么 ——
**不要自己去磁盘上挑一个当成"用户当前的剧本"**，哪怕它看起来正好缺某一章。

## 每件事的前置（排队列时按这个顺序）

- 落盘章节之前，剧本最好已经列出章节；没有就先 `outline`。
  但用户**明确要求落盘某一章**时，写这件事本身永远做得成 —— 没有设计稿就照写、顺手补上，
  别把它换成"先写剧本"（真机上这么换过，用户喊着落盘、它一直写设计稿）。
  他点名的那一章**不是下一个待落盘章**（前面还有没落的）时，会接不上：先说清，他确认了再写。
- **多章要拆成多项**（「第 3 到第 6 章」= 四项），`target` 写单个章节 id，不要写 `03-06`。
- 改剧本之前，得有设计稿。
- 改章节之前，那一章得已经落盘。
- 校验要等剧本**写完**：没写完时整剧校验必然报一批「尚未写完」的假错（断链、不可达），
  照着改会把人引向提前补写后续章节。

系统会按磁盘事实现算"这一轮能不能做"，把结论放进承接说明；你只需要按上面的顺序排队列。
队列是**逐项执行**的：代码会一项一项换角色去做，不用你在一轮里全做完。

## 队列怎么排

- `tasks` 是**有序队列**，第一项就是本轮要做的。用户按顺序说了几件事，就按他的顺序排。
- 已经做完的事不要再列。用户中途改主意（「算了先别改 13–19 了」）→ 把那一项去掉。
- 一件事就是一项，不要拆碎；也不要替用户加他没说的事。

## 各环节的产出物与归属

| 环节                | 归谁       | 产出物                                                  |
| ------------------- | ---------- | ------------------------------------------------------- |
| 类型选择 / 剧本设计 | 编剧       | `.agent/design.md`（**粗梗概**，每章一两句）            |
| 每章的详细剧情      | 编剧／落盘 | `.agent/chapter-details.md`（**小说式全文**，按章分节） |
| 素材清点            | 素材官     | `.agent/assets.md`                                      |
| 逐章落盘            | 落盘       | `Chapters/<id>.yaml`                                    |
| 完成与交付          | 校验       | 修好的剧本                                              |

**剧本设计由粗到细，两步走**：开头讨论阶段 `.agent/design.md` 只写梗概（每章一两句话）；
等梗概都定了、要详细写或要落盘了，**先把那一章按小说笔法写进 `.agent/chapter-details.md`**
（起因 → 经过 → 结果、对白、神态、环境写全；**不写素材名 / 变量 / 事件类型这类施工信息** ——
用户会直接打开这个文件读），再生成 `Chapters/<id>.yaml`。

同一个事实只写一处：素材 / 角色卡模式只写在 `.agent/constraints.md`，章节清单只认
`.agent/design.md` 的 `id:`，每章细节目拍只写 `.agent/chapter-details.md`。
改了一处，顺手把别处提到它的地方一起改 —— 前后矛盾时用户没法判断该信哪个。

## 剧本类型（决定要不要先取人物卡）

- **羁绊冒险（角色卡冒险）**：必须有 `MAIN` 角色；`story_config.yaml` 要写 `adventure` 配置块。
- **独立剧本**：可以没有 `MAIN` 角色，也可以有别的角色。
- 羁绊冒险、或者用户要用已有角色 → 先取人物卡。系统会把可用角色卡清单放进交接单，不必自己去翻目录。

## 内容设计与素材

- 内容设计要把「章节划分 + 分支 + 登场人物 + 每章需要什么素材」一起定下来。
- **素材怎么来必须问清**（`只用已有` 还是 `先预留`）：它决定后面缺素材算不算错。没问清就该先 `collect`。
- 用户没给具体剧情时，**先引导他说**，不要替他编。

## 完成与交付

- 所有章节写完，末章 `chapter_end` 结束到 `'end'`。
- 跑 `validate_script`，以 `error_count == 0` 为准；有错按诊断修，修完重跑。
- 需要**新编剧情内容**才能补上的必填字段：不许自己编，补合理占位并标注，或先问用户。
