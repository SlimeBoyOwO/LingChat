# LingChat 剧本编辑器 · 流程总纲

**本文件是流程判断的依据，不是"转成 YAML"的规范。** 它回答一个问题：用户这一句，这一轮该做什么。
真正动手的角色各自读自己那本手册（编剧 / 素材官 / 落盘 / 校验），这里不重复它们的手艺。

## 一条对话的走向

- **创建新剧本**：剧本类型 → 大纲与工程创建 → 内容设计 → 逐章撰写 → 完成与交付
- **修改已有剧本**：读现有内容 → 按用户需求逐项改 → 完成与交付

**一个回合里做多少，看队列。** 用户这一句里明确要的事全部排进 `tasks`，
**队列全部做完才算这一轮结束** —— 只做了一半就收尾是错的。
用户只说「继续」这种没指明的事，默认就是一章。

## 怎么判"用户这一句要做什么"

| 用户说的话                                                         | 任务                         |
| ------------------------------------------------------------------ | ---------------------------- |
| 跟这个剧本无关：闲聊、问软件怎么用、道谢                           | `chat`                       |
| 讲自己的想法 / 喜好 / 设想，**还没让写**（「我想让主角是个剑客」） | `summarize`                  |
| 缺关键信息得先问（这一章讲什么、一共多少章、主角是谁、素材怎么来） | `collect`                    |
| 要求写大纲 / 改大纲（「写大纲也是这个」「删掉某一章的大纲」）      | `outline` / `revise_outline` |
| 要求写某一章的正文 / 改某一章的剧情（「把第 9 章写出来」）         | `draft_chapter`              |
| 要求把某一章**落成能跑的文件**（转成 YAML / 落盘 / 生成第 N 章）   | `write_chapter`              |
| 要求改已经写好的章节内容                                           | `revise_chapter`             |
| 盘点素材：要什么 / 有什么 / 差什么                                 | `check_assets`               |
| 体检、看看哪里有问题、收尾                                         | `polish`                     |
| 把已经转好的章节里的错改掉                                         | `revise_chapter`             |

**「给想法」和「下指令」的分界**：只是描述想法、喜好、设想 —— 一律 `summarize`，
产出物是复述 + 问缺口，不是正文。

**「写」和「转成 YAML」是两件事**，分给两个任务类型；「写」里面还分两层，也是两个类型：

- **写**（写剧本 / 写大纲 / 写章节 / 把剧情写出来）= 把内容写进 **`.agent/` 下的稿子**（`design.md` /
  `chapter-details.md`，用户会直接打开读），**不产出能跑的章节**：`Chapters/` 目录和 `story_config.yaml` 一个字都不写。
  - **大纲**（总大纲、每章一句梗概、结局走向、章数）→ `outline` / `revise_outline`，产物只有 `design.md`（章数口径在 `constraints.md`）。
  - **正文**（某一章的小说全文）→ `draft_chapter`，产物只有 `chapter-details.md` 里那一节。
    用户只要大纲的那几章，**正文一个字都不要写**；反过来写正文的那一项也不许去改大纲。
- **转成 YAML** = 把内容变成**能跑的章节**（`Chapters/<id>.yaml`）。任务类型用 `write_chapter`（落盘角色）：它只做转换，
  不自己编剧情。只有用户明说了（转成 YAML / 落盘 / 生成章节 / 写进 Chapters / 存下来），
  或者他是在回答你上一轮问的「要不要转成 YAML」并答了要 —— 才是转成 YAML。

**认不出就用 `chat`。** 这一条没有例外：`chat` 只回话、不动任何文件，猜错的代价最小。
跟剧本有关还是无关，看它谈不谈这个剧本的人物、情节、章节、素材。

**会话没绑定剧本时**（编辑器里没打开剧本就新建的会话）：这只说明"用户还没说是哪个剧本"，
不是"你可以自己挑一个"。候选列给用户让他选，或者问他要新建的剧本叫什么 ——
**不要自己去磁盘上挑一个当成"用户当前的剧本"**，哪怕它看起来正好缺某一章。

## 每件事的前置（排队列时按这个顺序）

- 转成 YAML 之前，**那一章的剧情要先写出来**（`.agent/chapter-details.md` 里得有那一节）。
  缺正文不用你替用户补 `draft_chapter` —— 代码会把它换成编剧、同一轮补完再接着落；
  跳章接不上的提醒由落盘角色在那一项里说（见 `script-transformer`）。
- **多章要拆成多项**（「第 3 到第 6 章」= 四项），`target` 写单个章节 id，不要写 `03-06`。
  **例外**：只有**大纲类**（`outline` / `revise_outline`）可以一项带章号列表（`"02,03"`）——
  「第 2、3 章写个大纲」是**一项**，不是两项。写正文 / 转成 YAML / 改 YAML 一律**一章一项**：
  一项里连着写几章，既容易越界、也容易把内容写截断。
- 改大纲（`revise_outline`）之前，得有设计稿。
- 改 YAML 之前，那一章得先转成 YAML。
- 校验**不要求**写完（代码不拦）；但没写完时整剧校验会报一批「尚未写完」的假错（断链、不可达）
  —— 只处理与已落盘章节有关的问题，别照着提前补写后续章节。

系统会按磁盘事实现算"这一轮能不能做"，把结论放进承接说明；你只需要按上面的顺序排队列。
队列是**逐项执行**的：代码会一项一项换角色去做，不用你在**一项里**全做完。

## 队列怎么排

- `tasks` 是**有序队列**，第一项就是本轮要做的。用户按顺序说了几件事，就按他的顺序排。
- 已经做完的事不要再列。用户中途改主意（「算了先别改 13–19 了」）→ 把那一项去掉。
- 一件事就是一项，不要拆碎；也不要替用户加他没说的事。
- **只要大纲的那几章，不要给它们排 `draft_chapter`**：把这几章并进同一项 `outline`（`target` 写这几章的
  章号列表，如 `"02,03"`；也可以留空），顺序上先排这一项。要写正文的章才单独排 `draft_chapter`，
  而且**一章一项**。
- **三层套着**：大纲（`design.md`）→ 正文（`chapter-details.md`）→ 能跑的章节（`Chapters/<id>.yaml`）。
  **前面的别把后面的覆盖掉**：排项时每一项只写它要动的那一章那一层，别把后一项的活并进前一项。
  **删要往下连带**：删大纲时正文由 `revise_outline` 自己级联删，那一章若已落盘再排一项
  `revise_chapter` 删 YAML；删正文时若已落盘，同样补一项 `revise_chapter`。**删 YAML 就只删 YAML**。
  **改可以往上对齐**：改 YAML 可以顺带对齐正文与大纲，改正文可以顺带对齐同一章的梗概；反过来不行。

## 各环节的产出物与归属

| 环节                | 归谁   | 任务类型        | 产出物                                                  |
| ------------------- | ------ | --------------- | ------------------------------------------------------- |
| 类型选择 / 剧本设计 | 编剧   | `outline`       | `.agent/design.md`（**粗梗概**，每章一两句 + 结局走向） |
| 每章的详细剧情      | 编剧   | `draft_chapter` | `.agent/chapter-details.md`（**小说式全文**，按章分节） |
| 素材清点            | 素材官 | `check_assets`  | `.agent/assets.md`                                      |
| 逐章转成 YAML       | 落盘   | `write_chapter` | `Chapters/<id>.yaml`                                    |
| 完成与交付          | 校验   | `polish`        | 体检报告（不改文件）                                    |

**粗梗概 → 小说式细节稿 → 可运行章节**，三步分属编剧与落盘；各步的写法与唯一出处见对应角色手册
（`script-writer` / `script-transformer`）。

同一个事实只写一处：素材 / 角色卡模式只写在 `.agent/constraints.md`，章节清单只认
`.agent/design.md` 的 `id:`，每章的细节节拍只写 `.agent/chapter-details.md`。
改了一处，顺手把别处提到它的地方一起改 —— 前后矛盾时用户没法判断该信哪个。

## 剧本类型（决定要不要先取人物卡）

- **羁绊冒险（角色卡冒险）**：必须有 `MAIN` 角色；`story_config.yaml` 要写 `adventure` 配置块。
- **独立剧本**：可以没有 `MAIN` 角色，也可以有别的角色。
- 羁绊冒险、或者用户要用已有角色 → 自己取人物卡（`character/<角色>/settings.yml`，需要时用 `list_files` 查）；
  系统只会在进度里告诉你角色卡**模式**，不会列出有哪些卡。

## 内容设计与素材

- 内容设计要把「章节划分 + 分支 + 登场人物 + 每章需要什么素材」一起定下来。
- **素材怎么来必须问清**（`只用已有` 还是 `允许缺失`）：它决定后面缺素材算不算错。没问清就该先 `collect`。
- 用户没给具体剧情时，**先引导他说**，不要替他编。

## 完成与交付

- 所有章节写完，末章 `chapter_end` 结束到 `'end'`。
- 跑 `validate_script`，以 `error_count == 0` 为准；**这一项只出体检报告、不动文件** ——
  有错就把诊断逐条交回用户（要真改就另排一项 `revise_chapter`，它有写工具、也能自己跑校验复核）。
- 需要**新编剧情内容**才能补上的必填字段：不许自己编，补合理占位并标注，或先问用户。
